# АЛГОРИТМ РАБОТЫ НАД ПРОЕКТОМ (согласован с заказчиком)

Документ фиксирует **порядок работы**, а не техническое задание. Технические
требования — в `01_ТЗ.md`, план CP/M — в `04_ПЛАН_CPM.md`, план тестов — в
`02_ПЛАН_ТЕСТИРОВАНИЯ.md`, хроника сборки — в `03_ЖУРНАЛ_СБОРКИ.md`.

---

## 1. АЛГОРИТМ (задан заказчиком, выполняется буквально)

1. **Спрашиваю то, что непонятно.**
2. **Пишу план работ.**
3. **Согласовываю план** — но НЕ во время работы (правки вносятся после).
4. **Пишу тесты к тому, что планируется в итоге** (до выполнения работ, а не после).
5. **Выполняю план работ.**
6. **Прогоняю написанные ранее тесты.** Если не прогоняются — правлю и прогоняю вновь.
7. **Если всё работает — прогоняю тесты ЕЩЁ РАЗ** (повторный прогон обязателен:
   первый может пройти на прогретом кэше или на невыгруженном состоянии).
8. **Вношу правки в «используемые планы»** (документы планов приводятся в
   соответствие с фактически сделанным).
9. **Пишу отчёт по выполненной работе.**

## 2. СОГЛАСОВАННЫЕ УСЛОВИЯ

| Вопрос | Решение заказчика |
|---|---|
| Какие тесты писать | Уровни **A** (проверки генерации) и **B** (тесты эмулятора), **T1–T4 достаточно** |
| Назначение тестов | **Для самопроверки агента**, НЕ приёмочные |
| Режим работы | **Режим Б**: план показываю в начале круга и сразу выполняю; заказчик корректирует по ходу |
| `build_archive` | удалить **после успешного прогона** |
| Отчёт | только при **полном отсутствии ошибок** |

## 3. ЖЁСТКИЕ ОГРАНИЧЕНИЯ ТЗ (нарушение = переделка)

* Логика процессора, CP/M и I/O-обвязки — **только FBD**; ST допустим лишь для
  инициализации памяти и генерации тестовых данных.
* **CFC не использовать.** Готовые библиотеки эмуляторов/CP/M не использовать.
* Один такт 8080 = один скан PLC; порядок обеспечивается Execution Order.

## 4. ПРИВЯЗКА АЛГОРИТМА К ФАЗАМ

| Шаг алгоритма | Фаза | Состояние |
|---|---|---|
| 1–3. Вопросы, план, согласование | — | **выполнено** |
| 4. Тесты написаны | `02_ПЛАН_ТЕСТИРОВАНИЯ.md` | **выполнено** (199 кейсов + CP/M + I/O) |
| 5. Выполнение плана | фазы A–F | **в работе** |
| 6. Прогон тестов и правка | фазы B–E | **в работе** |
| 7. Повторный прогон | фаза G | ожидает |
| 8. Правки в планы | фаза G | ожидает |
| 9. Отчёт | фаза G | ожидает |

### Фазы

* **A. База после перезапуска.** Полная сборка, подтверждение «0 ошибок + RUN».
* **B. Отладка прогонного автомата `TEST_8080`** — блокирует все 199 тестов:
  регистры не доходят до процессора через порт CP/M.
* **C. 199 тестов ядра → 100 % PASS.**
* **D. Тесты CP/M → PASS** (приглашение, эхо, каталог, TYPE, счётчики).
* **E. Тесты I/O → PASS** (OUT/IN, порт без канала, путь IN через процессор, watchdog).
* **F. Закрытие пунктов ТЗ:** реальный `.COM`, прерывания, VISU, профиль 8 МБ,
  снятие заглушек BIOS LIST/PUNCH/READER и BDOS 24.
* **G. Финал:** повторный прогон, правки в планы, удаление `build_archive`, отчёт.

## 5. ПРАВИЛА, ВЫВЕДЕННЫЕ ПО ХОДУ РАБОТЫ (обязательны к соблюдению)

1. **Ошибка компиляции локализуется КОМПИЛЯТОРОМ, а не глазами.** В headless-режиме
   CODESYS не печатает имя POU, поэтому применяется бисекция по телам → сетям →
   элементам → сетям зависимости → элементам зависимости
   (`gen_bisect2.py` + `tools/run_bisect*.ps1`).
2. **Бисекция обязана оставлять проект самосогласованным:** опустошать ТЕЛА
   (интерфейс сохраняется) и удалять только СУФФИКС сетей/элементов — ссылки в
   FBD идут назад, поэтому префикс всегда корректен, а произвольное подмножество
   рвёт XML.
3. **Пустое тело вызывающего МАСКИРУЕТ ошибку в вызываемом.** Тело зависимости
   генерируется только если её вызывают: прежде чем объявить зависимость чистой,
   надо убедиться, что её кто-то вызывает живым.
4. **Любая проверка обязана измерять свой ОХВАТ** (сколько связей проверено,
   сколько осталось неразобранными) — иначе «0 ошибок» ничего не значит.
5. **Вызов FB объявляет только те выводы, которые читаются, и в порядке чтения**
   (`fbd_xml.Pou._prune_outputs`), проверка — `tools/check_outpins.py`.
6. **Имя файла лога обязано совпадать с именем скрипта**, запускаемого раннером,
   иначе раннер повторяет прогон 8 раз.
7. **Не запускать два прогона одновременно**: CODESYS однопроцессный, соседний
   проект снимает наш процесс.
8. **Инструменты проверки без CODESYS** (`tools/check_*.py`) прогоняются ПЕРЕД
   сборкой: они находят дефекты за секунды там, где сборка стоит минуты.
