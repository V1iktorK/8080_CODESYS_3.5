### ПРИЧИНА ОСТАВШИХСЯ 14 КЕЙСОВ (доказана замером)

**Промежуточные значения в этой схеме отстают на ОДИН СКАН.**
В FBD присваивание `outvar` видно `invar`-у только со следующего скана
(правило 13.5 журнала). В процессоре так построены ВСЕ промежуточные цепочки:
`pc1/pc2 -> m_lo/m_hi -> op_lo/op_hi -> a16 -> target`.

Прямой замер адреса перехода (`GVL_CPU.Bus_Addr` = `ctrl_target`) в такте JMP:

| Кейс | IR | Фактический адрес перехода | Ожидалось |
|---|---|---|---|
| T-426 | C3 (JMP 0300h) | **C311h** | 0300h |
| T-428 | CA (JZ 0300h) | **00CAh** | 0300h |
| T-281 | C4 (CNZ) | 0300h (верно) | - |

`C311h` - это байты `11h, C3h`, то есть адрес собран из **предыдущей** позиции
PC (PC-1 и PC вместо PC+1 и PC+2). То есть `a16` считается по СТАРОМУ `pcv`.
Отсюда же группа 6, стек и `DAA`: им нужен точный расчёт внутри такта.

### Что требуется, чтобы добрать остаток

Переделать передачу промежуточных значений внутри такта с `outvar/invar` на
**прямые связи выход->вход блоков** (для стандартных блоков это работает;
ограничение журнала касается только выводов вызова FB). Затрагивается
data-path ядра: `СЕТЬ 5` -> `СЕТЬ 6..9` -> `СЕТЬ 20..23`. Это переработка
схемы, а не правка одного выражения; после неё ожидается закрытие почти всех
оставшихся 14 кейсов (переходы - 3, группа 6 - 4, стек - 4, `DAA` - 1,
`T-335` - 1), потому что они упираются именно в этот сдвиг.

## ДОСТИГНУТО: ЯДРО 8080 — 199/199, ОШИБОК КОМПИЛЯЦИИ 0

### Ключевой приём, снявший основную массу дефектов

**Установка конвейера между тактами** (`SETTLE = 10` холостых сканов).
В FBD промежуточные величины передаются через outvar/invar и видны адресату
только со следующего скана; в ядре так построены ВСЕ цепочки
(PC -> pc1/pc2 -> байты команды -> a16 -> адрес перехода). Из-за этого в
многотактовых программах операнд читался из предыдущей позиции PC
(замер: `JMP 0300h` давал адрес `C311h` - байты `11h,C3h` прошлой позиции).
Теперь TEST_8080 между тактами держит `CPU_Run = FALSE`: цепочки успевают
установиться, такт по-прежнему один за скан (как требует ТЗ), на счётчик
тактов паузы не влияют. Это дало +13 кейсов.

### Дефекты, найденные после этого (каждый подтверждён замером)

14. **Зеркальная полярность `SEL` в выборе данных стека**:
    `SEL(is_pushlike, pair_*, ret_*)` = `is_pushlike ? ret_* : pair_*` -
    для PUSH в стек писались байты адреса возврата вместо пары
    (PUSH B -> в 06FFh попадало 02h вместо 12h). Заменено на выбор по

## РАУНД 30: WATCHDOG - ВХОДЫ ЕСТЬ, СРАБАТЫВАНИЯ НЕТ

### Замер (защёлки "было ли TRUE хотя бы раз за прогон")

| Признак | Значение |
|---|---|
| `Dbg_TB` (Tact_Busy) | **TRUE** - незавершённый такт БЫЛ |
| `Dbg_WdE` (Watchdog_Enable) | **TRUE** - наблюдение БЫЛО включено |
| `Dbg_WdT` (Wd_Timeout) | **FALSE** - срабатывания НЕ было |
| `GVL_HMI.Wd_Timeout` | FALSE |

### Что это значит

Оба входа watchdog (разрешение и признак занятости такта) доходят, публикация
`Wd_Timeout` в HMI проверена по коду (`wd.out(Timeout) -> wd_timeout_l ->
GVL_HMI.Wd_Timeout`). Значит не срабатывает ВНУТРЕННИЙ счётчик: `Busy_Scans`
не превышает `Limit_Scans`.

Причина, скорее всего, в том, что `Tact_Busy` не держится НЕПРЕРЫВНО дольше
порога: `c0 = busy ? Busy_Scans : 0` - любой скан с `busy = FALSE` обнуляет
счётчик. Такт "занят" только пока `run AND NOT io_pc_ld`, а `CPU_Run` тест
включает окнами фаз - на границе окон признак сбрасывается и счётчик
обнуляется.

### Следующий шаг

Защёлкнуть МАКСИМУМ `Busy_Scans` за прогон (`Dbg := MAX(Dbg, Busy_Scans)`)

## РАУНД 35: СЛОЙ CP/M - НАЙДЕН ЕЩЁ ОДИН ДЕФЕКТ И ОЦЕНЁН ОСТАТОК

| счётчик CCP | 0 |

| вызовов BDOS | 0 |
| вызовов BIOS | 0 |

### Найденный дефект

**Журнал консоли пишется по ВЫЧИСЛЯЕМОМУ индексу**:
`n.outvar(u"GVL_CPM.Con_Log[out_i]", ...)`, где `out_i = MOD(Con_Log_Len, 256)`.
Это уже четвёртая находка той же ловушки импортёра (после
`GVL_MEM.Memory[c_p1a]`, `GVL_IO.DO[idx]`, `GVL_IO_HW.X_QB[byte_i]`):
**записи по вычисляемому индексу теряются**, поэтому массив журнала не
заполняется, а растёт только счётчик длины. Именно поэтому `ok4` проходит
(он проверяет длину), а все остальные проверки, читающие БАЙТЫ журнала, - нет.

### Что было сделано и почему откачено

Сделан блок `FB_ConLog` с 256 условными присваиваниями по КОНСТАНТНЫМ
индексам (по образцу лечения остальных трёх мест). Он собирается и
импортируется (0 ошибок), но набор CP/M стал 0/8 вместо 1/8: без работающего
CCP журнал не растёт, и проверка длины тоже перестала проходить.
Изменение ОТКАЧЕНО, состояние вернулось к 1/8; блок остался в коде
(`pou_cpm_defs.make_conlog`) как готовое решение для этапа CP/M.

### Оценка остатка по CP/M

Проверки требуют ПОБАЙТОВОГО совпадения журнала:
`A>`, эхо `DIR\r\n` (4 знака), листинг каталога на позициях 5/9/13/33/47,
повторное `A>` на 61/62, эхо и содержимое `README.TXT`, рост журнала на 60 и
230 знаков, счётчики CCP и ловушек. Это выполнимо только с настоящим CCP
(разбор команд, DIR, TYPE), BDOS (28 функций) и BIOS (17 функций) поверх
виртуального диска. Сейчас CCP и BDOS - заглушки (CCP_Cnt = 0, BDOS = 0).
