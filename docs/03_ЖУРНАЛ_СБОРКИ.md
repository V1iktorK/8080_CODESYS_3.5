# ШАГ 3. ЖУРНАЛ СБОРКИ: генерация FBD-схем в CODESYS 3.5 SP17

Здесь собраны все правила и «грабли» программной генерации FBD. Каждое правило
получено экспериментом, а не из документации, — документации по этому диалекту нет.

---

## 1. Как запускается сборка

```powershell
powershell -File 8080_EMU\generator\tools\run_codesys.ps1 -Script <путь\к\скрипту.py>
```

Скрипт исполняется внутри CODESYS:
`CODESYS.exe --profile="CODESYS V3.5 SP17 Patch 3" --runscript=<...> --noUI`

**Обязательно с автоповтором.** CODESYS — single-instance приложение. Если предыдущий
headless-процесс не освободил мьютекс, следующий запуск **молча** завершается с кодом 1:
пустой stdout, пустой лог скрипта. Внешне это неотличимо от ошибки в скрипте.
`run_codesys.ps1` убивает хвостовые процессы, ждёт завершения и повторяет
попытку, пока лог не станет непустым (обычно хватает 1–2 попыток).

## 2. Скелет проекта (подшаг 0)

Поставляемые шаблоны (`Templates\Standard.project`, `Empty.project`) ссылаются на
устройство `PLCWinNT` v3.1.3.0, которого в этой установке нет → `C188: Устройство
не установлено в систему. Генерация кода невозможна`. Метода `add_device` в API нет.

Решение — найдено в дампе API (`system.dump_scripting_api()`):
интерфейс `IScriptProjectDeviceExtension` («Projects which can contain devices»)
предоставляет метод **`add`**:

```python
proj = projects.create(path)
proj.add(name=u"Device", type=4096, id=u"0000 0001", version=u"3.5.17.30")
app = proj.active_application        # Plc Logic -> Application создаётся автоматически
```

`type=4096` — семейство CODESYS Control Win V3; установленная версия 3.5.17.30
(проверено по `C:\ProgramData\CODESYS\Devices\4096\0000 0001\`).

GVL и DUT создаются штатным API и заполняются **текстом**:

```python
gvl = app.create_gvl(u"GVL_...");  gvl.textual_declaration.replace(text)
dut = app.create_dut(u"ST_...", type=DutType.Structure); dut.textual_declaration.replace(text)
```

## 3. Диалект PLCopenXML для FBD — правила

Все проверены на живом CODESYS 3.5 SP17 Patch 3.

| № | Правило | Что будет, если нарушить |
|---|---|---|
| 1 | Тело: `<body><FBD> …элементы… </FBD></body>`, **без** обёртки `<network>` | — |
| 2 | `localId` уникальны **внутри всего POU**, а не внутри сети | `<connection>` попадает на чужой элемент, связи молча теряются (из 4 входов выжил 1) |
| 3 | Порядок детей `<block>`: `position` → `inputVariables` → **`inOutVariables`** → `outputVariables` | импорт падает: «Элемент block имеет недопустимый дочерний элемент outputVariables» |
| 4 | `<inOutVariables />` обязателен, даже пустой | см. п. 3 |
| 5 | `<interface>` **не может быть пустым**. Нужны и структурный `<interface>`, и текстовый дубль в `addData/InterfaceAsPlainText` | `import_xml` «проходит успешно», но POU в проекте **не появляется** |
| 6 | **Один выход = ровно одна связь.** Это относится и к `<inVariable>`, и к выходам блоков | CODESYS молча выбрасывает **весь POU** (см. раздел 4.3 и 4.4) |
| 7 | `formalParameter` у `<connection>` можно опускать — сопоставление по позиции | — |
| 8 | Координаты `x/y` при импорте игнорируются, CODESYS раскладывает схему сам | позиции из XML не сохраняются (но мы их пишем — для читаемости и переносимости) |
| 9 | Вызов пользовательского FB: `<block typeName="FB_X" instanceName="inst">`, экземпляр объявлен в `VAR` | CODESYS сохраняет `instanceName` при обратной выгрузке (проверено) |

### Проверенные стандартные операторы

Работают и импортируются корректно (каждый проверен отдельным минимальным POU):

`AND`, `OR`, `XOR`, `NOT` (BOOL и BYTE) · `ADD` · `SEL(G, IN0, IN1)` ·
`MOVE(IN)` · прямое присваивание `<inVariable> → <outVariable>` ·
POU с несколькими выходами · каскад блоков · 8 сетей в одном POU.

## 4. Три бага генератора, найденные и исправленные

### 4.1. Конфликт `localId` между сетями
Сети нумеровались «с единицы» каждая. Поскольку `<FBD>` — плоский контейнер,
ссылки попадали на чужие элементы. **Исправлено:** сквозной счётчик в `Pou`.

### 4.2. Пустой `<interface>`
Первая версия генератора писала объявления только текстом
(`InterfaceAsPlainText`). CODESYS сообщал об успешном импорте, но объект не создавался.
**Исправлено:** `Pou` строит полноценный `<interface>` (`inputVars`/`outputVars`/`localVars`)
и дублирует его текстом.

### 4.3. Повторное использование одной входной переменной — САМОЕ КОВАРНОЕ
Бисекция из 12 минимальных POU показала: теряется ровно тот POU, где одна
`<inVariable>` питает **два и более** входа (там переменная `LD` шла в два `SEL`).

```
T_BOOL_AND  ЕСТЬ      T_BYTE_OR   ЕСТЬ
T_BOOL_OR   ЕСТЬ      T_SEL       ЕСТЬ
T_BOOL_XOR  ЕСТЬ      T_MOVE      ЕСТЬ
T_BOOL_NOT  ЕСТЬ      T_ASSIGN    ЕСТЬ
T_BYTE_ADD  ЕСТЬ      T_TWO_OUT   ЕСТЬ
T_BYTE_AND  ЕСТЬ      T_TWO_SEL   ПОТЕРЯН   <-- единственный с повтором
```

Это же погубило `FB_PackByte` и `FB_FullAdder` в первой сборке.

**Исправлено в генераторе:** `Network._expand_invars()` перед отрисовкой
размножает такие переменные — «одна ссылка = один элемент». Сам CODESYS при обратной
выгрузке снова их сливает, поэтому схема не разрастается, а потерь больше нет.

## 5. Контроль качества сборки

`codesys_build.verify_import()` после импорта:

1. ищет каждый POU в дереве проекта (обходом, а не через `app.find` — тот нестабилен);
2. выгружает импортированное обратно через `export_xml`;
3. сравнивает **число блоков** «сгенерировано» vs «после импорта»;
4. требует **ноль пустых входов** (`<connectionPointIn />` без связи).

Только после этого запускается `app.build()`. Сообщения компилятора CODESYS пишет
в stderr процесса — их читает `run_codesys.ps1` (`<скрипт>.stdout.txt.err`).

**Дополнительно:** POU импортируются **по одному файлу**. Пакетный импорт нескольких
POU одним XML терял часть объектов и не сообщал об этом.

## 8. Подшаг 3.2: АЛУ, коммутация, память, стек

### 8.1. Диалект вызова пользовательского FB (проверено)

```xml
<block localId="4" typeName="FB_FullAdder" instanceName="fa0">
```
Экземпляр объявляется в `VAR` (можно массивом или по одному). CODESYS принял
и сохранил `instanceName` при обратной выгрузке — это рабочий способ.

### 8.2. Баг №4: fan-out убивает POU не только у переменных

Бисекция №2 (5 минимальных POU):

```
T_FANOUT_A   ПОТЕРЯН   выход блока идёт на ДВА входа в одной сети
T_CROSS_B    ЕСТЬ      выход блока используется в следующей сети
T_CROSS_C    ЕСТЬ      выход блока используется в двух разных сетях
T_INDEP_D    ЕСТЬ      две независимые сети (контроль)
T_VAR_E      ЕСТЬ      передача между сетями через переменную
```

**Вывод:** губит именно разветвление выхода (fan-out), а межсетевые ссылки легальны.
Правило общее для любых источников — и переменных, и блоков.

**Исправлено:** `Pou._expand_fanout()` разворачивает граф схемы в дерево:
на каждое лишнее использование создаётся копия элемента вместе со всей входной
ветвью и вставляется непосредственно перед потребителем (ссылка всегда «назад»).
Счёт ведётся по паре **(элемент, имя вывода)** — разные выводы одного блока это
разные источники, иначе `ua.B0..B7` ложно считались бы fan-out ×8.

**Плюс защита:** попытка размножить выход вызова FB даёт явную ошибку
(экземпляр один) — это ошибка проектирования, а не молчаливая потеря POU.

### 8.3. Баг №5: процесс-сирота блокирует все запуски

`CODESYS.exe`, зависший после одного из прогонов, держит мьютекс single-instance.
Все последующие headless-запуски молча выходят с кодом 1 (пустой stdout, пустой лог).
`Stop-Process` его не берёт. **Исправлено:** в `run_codesys.ps1` используется
`taskkill /F /T /IM CODESYS.exe`.

## 9. Подшаг 3.3: шина управления, флаги, декодер, блок управления

### 9.1. Баг №6: чтение выхода вызова FB из последующей сети ВЕШАЕТ импорт

`FB_FlagsReg` (объединяющий распаковку PSW, защёлкивание флагов и упаковку PSW)
зависал на импорте намертво: CODESYS не падал и не сообщал об ошибке — процесс
висел до принудительного убийства. Бисекция из трёх урезанных вариантов
(`probe_flags.py`) показала, что по отдельности всё работает:

```
V1_UNPACK  (только распаковка PSW)          ЕСТЬ
V2_FLAGS   (только флаги с защёлкиванием)   ЕСТЬ
V3_PACK    (флаги + упаковка PSW)           ЕСТЬ
```

Причина — комбинация: выход вызова FB (`up.B7`) читался напрямую из сетей 2..6,
где при этом есть обратная связь по записываемому флагу.

**Правило, добавленное в генератор и в стиль схем:** выход вызова FB нельзя не
только разветвлять (баг №4), но и **читать из другой сети** — его надо сразу
защёлкнуть в переменную POU. После защёлкивания восьми бит `PSW_In` в `pb0..pb7`
импорт проходит с первой попытки.

## 10. Подшаг 3.4: регистровый файл, FB_CPU8080 и PLC_PRG — ШАГ 3 ЗАКРЫТ

### 10.1. Новое правило диалекта: разрядность при 16-разрядных операциях

`SHL(BYTE, 8)` в FBD работает **в разрядности BYTE** и даёт ноль — старший байт
адреса теряется. Чтобы собрать 16-разрядное значение из двух байт, байт нужно
сначала перенести в переменную типа `WORD` (расширение BYTE→WORD выполняется
присваиванием), и только потом сдвигать:

```
h_w := regs.H;                       (* BYTE -> WORD *)
hl  := SHL(h_w, WORD#8) OR l_w;
```

Это же применено при сборке адреса перехода из байтов `PC+1` и `PC+2`.

### 10.2. Про пять экземпляров памяти

`FB_Memory64K` вызывается **один раз за скан**, а процессору нужны обращения по
разным адресам в одном такте: выборка команды по `PC`, операнд по `HL`, младший
и старший байты по `PC+1`/`PC+2`, запись результата. Поэтому в `FB_CPU8080`
пять независимых экземпляров блока, работающих с одной и той же `GVL_MEM.Memory`.
Разделение по экземплярам, а не по MUX адреса — единственный способ уложить
все обращения в один вызов.

### 11.2. Баг №7: связь «вывод вызова FB → вход блока» теряется МОЛЧА

Симптом ровно один: `ПОСЛЕ ИМПОРТА: блоков=697` вместо `699`. При этом ни один
POU не потерян, пустых входов нет, компиляция проходит без ошибок и предупреждений.
То есть контроль качества поймал потерю, а CODESYS о ней не сообщил.

Как искали (приём стоит взять на вооружение): сравнили **подписи элементов** —
для каждого `SEL` построили тройку (тип/выражение `G`, `IN0`, `IN1`) в
сгенерированном XML и в выгрузке и сравнили мультимножества (`analyze_sel.py`).
Пропали ровно два `SEL` — те, через которые считался адрес следующей команды
`PC_Next`, — и вместе с ними вся ветвь ниже по схеме.

Причина: это было **единственное** место в проекте, где вывод вызова FB подавался
непосредственно на вход блока:

```xml
<variable formalParameter="IN1">
  <connectionPointIn>
    <connection refLocalId="735" formalParameter="PC_Next" />   <!-- вывод FB_ CtrlUnit -->
```

`formalParameter` на связи в `outVariable` CODESYS понимает (так собраны все
подшаги 3.2–3.4), а на связи **во вход блока** — теряет элемент и всё, что от него
запитано. Отдельный `SEL` с одним входом от FB в пробе не проверялся: в `FB_ALU8`
такая связь есть, но там она ссылается на **одновыходной** `FB_PackByte`, и
импортёр, судя по всему, обходится без имени вывода.

**Правило (дополняет п. 9.1):** выход вызова FB защёлкивается в переменную POU
**всегда** — даже если он нужен в той же сети. Связь «вывод FB → вход блока»
не использовать. После правки: `742 из 742`.

### 11.3. Баг №8 (инфраструктура): раннер принимает лог ПРОШЛОГО запуска за успех

`run_codesys.ps1` считает попытку удачной по «лог в рабочей папке непустой».
Если этот же скрипт уже запускался, лог от прошлого раза лежит на месте, и при
мгновенном выходе CODESYS (чужой мьютекс — п. 8.3) раннер **не делает повторных
попыток**, а печатает старый лог. Внешне это выглядит как «сборка прошла», хотя
скрипт не выполнялся ни секунды.

Лечение: одна строка в раннере — удалять рабочий лог до цикла попыток. Заодно
перед запуском стоит убедиться, что процессов `CODESYS.exe` не осталось вовсе.

### 11.5. Нюансы унаследованного `FB_ALU8` (блок не менялся — подшаг 3.2 проверен)

При подключении полного набора команд выяснилось, что `FB_ALU8` трактует флаги
«по-сумматорному», а 8080 — «по-вычитательному». Блок не трогали, ядро
компенсирует это в такте:

* выход `CY` — это перенос сумматора `c8`, а в 8080 CY после `SUB/SBB/CMP` — это
  **заём**, то есть `NOT c8`; ядро инвертирует CY и AC для вычитающих операций;
* вход `Cin` подмешивается к **любой** операции, поэтому для всех команд, кроме
  `ADC/SBB/ACI/SBI`, ядро подаёт `Cin := 0` (иначе `ADD` при CY=1 прибавлял бы лишнюю единицу);
* AC для `ANA/ANI` в 8080 равен `A3 ИЛИ B3`, блок отдаёт жёсткую единицу — ядро
  считает AC для этих команд само.

### 12.2. Доступ CP/M к регистрам процессора — порт CP/M

Регистровый файл лежит внутри `FB_CPU8080_FULL`, а BDOS обязан читать C/DE/BC
и писать A/HL/PC/SP. Решение: **порт доступа со стороны CP/M**, добавленный в
ПОУ ядра НОВЫМ модулем (сам `pou_cpu_full.py` не правится).

```iecst
(* входы, добавленные в интерфейс FB_CPU8080_FULL *)
CPM_WE   : BOOL;   (* разрешение записи со стороны CP/M *)
CPM_Sel1 : BYTE;   CPM_Data1 : WORD;   CPM_LD1 : BOOL;   (* канал 1 *)
CPM_Sel2 : BYTE;   CPM_Data2 : WORD;   CPM_LD2 : BOOL;   (* канал 2 *)
(* выходы *)
CPM_A..CPM_L : BYTE;  CPM_PC, CPM_SP : WORD;  CPM_PSW : BYTE;
```
`CPM_Selk`: 0=A 1=B 2=C 3=D 4=E 5=H 6=L 7=PC 8=SP 9=Flags. Запись при
`CPM_WE AND CPM_LDk`; для A..L и флагов берётся младший байт `CPM_Datak`.

Как это сделано внутри (важно для будущих правок ядра):
1. **Чтение** — последняя сеть ПОУ защёлкивает `regs.A..L`, `pc.Q`, `sp.Q`,
   `flags.PSW` в переменные POU и выкладывает их в выходные порты.
2. **Запись — не вторым вызовом регистрового файла** (экземпляр один), а
   «подмешиванием» сигналов CP/M к штатным сигналам такта: сеть дешифрации
   порта ставится ПЕРЕД сетью регистрового файла, а в существующие вызовы
   `FB_RegFileQ`, `FB_Reg16` (PC/SP) и `FB_FlagsReg2` добавляются `SEL` и `OR`
   по входам `Data1/Dst1/Wr1`, `Data2/Dst2/Wr2`, `D/LD`, `PSW_In/LD_PSW`.
   Во время трапа процессор такт не выполняет (`run_i = FALSE`), поэтому
   конфликта двух источников нет.
3. Код регистра, который ждёт `FB_RegFileQ` (0=B…5=L, 7=A), получается из кода
   CP/M как `(код + 7) AND 7` — две операции, без таблиц.

Порт применяет запись на СЛЕДУЮЩЕМ скане (процессор вызывается первым и читает
`GVL_CPM.CPM_*`), поэтому фазы записи регистров в трапе занимают по одному скану.

### 12.3. Механизм трапа (FB_CPM_Trap)

В памяти лежат настоящие точки входа: `0000h: JMP 0E003h`, `0005h: JMP 0F000h`,
`0008h: JMP 0F000h`, таблица BIOS `0E000h` (17 записей по 3 байта
`JMP 0FE00h+3*i`). Программа делает `CALL 0005h` — процессор выполняет `JMP` и
PC оказывается на адресе-ловушке. Автомат трапа (поле `GVL_CPM.Trap_Phase`):

| Фаза | Что делает |
|---|---|
| 0 | старт: `PC := 0100h` через порт CP/M |
| 1 | старт: `SP := 0F200h` |
| 8 | рабочий режим: ждём `PC` на ловушке |
| 3 | трап: `CPU_Enable := FALSE`, `Ret_Addr := Memory[SP] + Memory[SP+1]<<8`, `Ret_SP := SP+2`, диспетчер выполняет функцию |
| 4, 5, 6 | запись результата: A, H, L (HL — только если `Ret_HL_En`, иначе HL сохраняется) |
| 7 | запись `PC := Ret_Addr` (или `Jump_PC` для WBOOT/загрузчика) и `SP` |
| 9 | снятие трапа, `Func_Done := FALSE`, возврат в фазу 8 |

Диспетчер ставит квитанцию `GVL_CPM.Func_Done`; пока её нет, `Enable` функций
держится, поэтому многосканные операции (CONIN, PRINTSTR, проход по каталогу)
работают без потери состояния. Процессор на это время стоит — это ровно
поведение из плана (раздел 7).

Циклов в FBD нет, поэтому дисковый движок `FB_CPM_DirEngine` просматривает
**одну запись каталога за скан** (64 скана на полный проход), а перенос записи
128 Б делается одной сетью.

### 12.5. Формат диска (упрощённый, заменяемый)

Каталог `0000h..07FFh` (64 записи по 32 Б, `st = E5h` — свободна), данные — блок
N (1 КБ) по адресу `N*1024`, блоки 0 и 1 заняты каталогом (DPB: SPT=32, BSH=3,
BLM=7, EXM=0, DSM=61, DRM=63, AL0=C0h, CKS=16, OFF=0). Файл занимает один
экстент (16 КБ), блоки выделяются последовательно (`GVL_CPM.Next_Block`),
освобождение блоков не делается. Доступ — байтовый (`GVL_DISK.Disk[адрес]`),
поэтому формат меняется без правки BDOS/BIOS.

**Правило безопасности (новое):** любой индекс массива в FBD надо держать в
границах. Адрес DMA маскируется `AND 0FF80h`, а адрес на диске строится
сдвигами (`SHL` усекает до 16 бит) — иначе сбойный FCB или чужой DMA дают
выход за границу массива и аварию ПЛК.

### 13.2. НОВОЕ ПРАВИЛО ГЕНЕРАЦИИ: порядок сетей = порядок ЧТЕНИЯ переменных

Самое важное открытие этого этапа. В FBD ссылка на переменную POU — это
`<inVariable>` с ИМЕНЕМ, а не ссылка на элемент по `localId`. Значит значение
читается в тот момент, когда элемент стоит в списке, а не «в конце скана».
Отсюда следствие, которое ломает автоматы молча:

```
сеть 2  : движок каталога (Start/Op) -> защёлкиваем Done/Result
сеть 25 : таблица переходов автомата читает эти защёлки
```

Если поменять сети местами (сначала переходы, потом движок), переходы читают
значения ПРОШЛОГО скана. `Done` движка — импульс в один скан, поэтому решение
принимается на скан позже, а `Done` к тому времени уже снят: автомат
застревает. Именно поэтому в `FB_CCP` движок и загрузчик стоят сетями 2 и 3,
а таблица переходов — последней.

### 13.3. НОВОЕ ПРАВИЛО СТИЛЯ: `SEL` и обёртка `IF`

`SEL(G, IN0, IN1)` возвращает `IN1` при `G = TRUE`. Перепутанные `IN0`/`IN1`
не видит НИ компилятор, НИ проверка связей — схема компилируется и «работает»,
только неправильно. В `pou_cpm_defs.py` добавлена обёртка:

```python
def IF(n, cond, a, b):      # = cond ? a : b
    return SEL(n, cond, b, a)
```

Все схемы CCP, загрузчика и новых частей движка написаны через `IF`. Для
многоуровневых выборов (автомат фаз) промежуточные результаты держатся в
именованных переменных Python — так полярность не перепутать.

### 13.4. НАЙДЕННАЯ ЛАТЕНТНАЯ ОШИБКА этапа 3.2: код возврата READSEQ

`res_d` считался по признаку фазы `ph2`, а `ph2` вычисляется в сети 6, то есть
в сети 4 (где считается `rd_ok`) он ещё держит значение ПРОШЛОГО скана. В
итоге перенос записи происходит, а `A` для READSEQ всегда получался `01h`
(«данных нет») — любая программа CP/M решила бы, что файл кончился, и `TYPE`
не работал бы. Исправлено: код возврата берётся по самим импульсам `rd_ok` /
`wr_ok`, которые истинны ровно в скане переноса. Ошибка была не видна ни
компилятору, ни контролю связей — её нашёл разбор протокола по сканам.

### 13.5. Read-modify-write одной переменной в одной сети — это норма

`x := IF(gate, x + 1, x)` и `out := IF(gate, new, out)` внутри одной сети
работают предсказуемо: второй элемент читает УЖЕ записанное значение. На этом
приёме построены счётчики (`srec`, `cpos`, `ec`, `tl`) и все условные записи.
Обратное тоже верно и опасно: если нужно СТАРОЕ значение, элемент чтения надо
ставить ДО элемента записи.

### 13.8. Формат диска: два профиля DPB, выбор константой

`DISK_PROFILE` в `pou_cpm_defs.py` — единственное место выбора; от него
считаются размер блока, раскладка каталога, карта занятости и адресация BIOS.

| Профиль | SPT | BSH | BLM | EXM | DSM | DRM | AL0 | AL1 | CKS | OFF | образ |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `FLOPPY_256K` (по умолчанию) | 26 | 3 | 7 | 1 | 242 | 63 | C0h | 00h | 16 | 2 | 256 КБ |
| `HARD_8M` | 128 | 5 | 31 | 1 | 2047 | 1023 | FFh | FFh | 0 | 0 | 8 МБ |

Раскладка (профиль FLOPPY_256K): `OFF*SPT*128 = 6656` Б системной области,
далее 2048 Б каталога (64 записи по 32 Б), далее 243 блока по 1 КБ. Запись
каталога `idx` лежит в секторе `DIR_SECT + (idx >> 2)`, байт `(idx AND 3) * 32`;
блок `N` начинается с сектора `DIR_SECT + N * (1 << BSH)`.

Размещение блоков — битовая карта `GVL_DISK.Alloc` (бит N = блок N занят),
начальное состояние которой задают AL0/AL1 плюс блоки демонстрационных
файлов; `DELETE` освобождает блоки удаляемой записи. Поиск свободного блока —
по ОДНОМУ блоку за скан (`FB_CPM_DirEngine`, фаза 4).

DPB (15 байт) лежит по `0FF00h`, DPH — по `0FF10h`, их читает программа.

### 14.2. Как реализованы `IN`/`OUT`: два скана на обращение (wait state)

Аппаратный слой обязан вызываться ПОСЛЕ процессора (иначе ломается проверенный
порядок «процессор -> трап -> диспетчеры CP/M»), поэтому обращение к порту
занимает два скана — как обращение к медленному устройству:

| Скан | Что происходит |
|---|---|
| N | процессор декодирует `IN d8`/`OUT d8`, выставляет `GVL_IO.Req`, `Port` (байт из памяти по `PC+1`), `WData` (регистр A), `RW`; `io_wait := TRUE`; PC **не** записывается, счётчик тактов **не** растёт |
| N | ниже по программе `FB_IO_Dispatch` выполняет обращение, ставит `GVL_IO.Ack` и (для `IN`) `GVL_IO.RData` |
| N+1 | процессор видит `Ack`: для `IN` пишет `A := RData` через порт 1 регистрового файла, снимает `io_wait`, PC := PC + 2, счётчик тактов +1 |

Ключевые детали:
* флаги `IN`/`OUT` не трогают: декодер и раньше ставил `C_WReg1..4 = FALSE` и
  `C_SZP_En/CY_En = FALSE`, то есть за это требование отвечает сеть 10 декодера;
* длина команды 2 байта: `PC := PC + 2` получается штатным путём (`C_Len = 2`,
  `is_branch = FALSE`), отдельной схемы не потребовалось;
* обмен идёт через шину `GVL_IO` (как ядро уже общается с `GVL_CPU`), поэтому
  **интерфейс `FB_CPU8080_FULL` не изменился** и вызов процессора в главной
  программе остался прежним;
* патчей готовых сетей ровно три: порт 1 регистрового файла (загрузка A),
  `LD` регистра PC (гашение на время ожидания) и вход `G` счётчика тактов.
  Всё — через `patch_block`/`patch_src_block` из `pou_io_defs.py`.

### 14.5. Адаптер C (реальный ПЛК): проверен компиляцией, но не проверен на железе

`FB_IO_Adapter_HW` объявляет физические адреса `%IB0`/`%QB0`/`%IW0`/`%QW0` — и он
**входит в основную сборку**. Так вышло потому, что сомнение разрешилось фактом:
сначала адаптер был отдельным неподключаемым POU (как и предполагало задание),
затем отдельная проба `gen_probe_hw.py` показала, что CODESYS Control Win V3
принимает такие объявления и БЕЗ модулей ввода-вывода:

```
GVL GVL_IO_HW создана (870 символов объявления)
импорт FB_IO_Adapter_HW OK          (115 блоков, все входы подключены)
Компиляция: Text: C0: Компиляция завершена -- 0 ошибок, 0 предупреждений
```
Поэтому адаптер добавлен в сборку (64-й POU) — в проекте теперь все ТРИ адаптера,
и все три компилируются. Активным остаётся тот, что задан константой
`ADAPTER_TYPE` (`pou_io_defs.py`), сейчас `FB_IO_Adapter_Sim`; адаптер HW
импортируется и компилируется, но не вызывается ни одной схемой.

ЧЕГО ЭТО НЕ ЗНАЧИТ: что обмен с физическими модулями работает. Модулей нет,
адреса ни с чем не связаны (в дереве устройства нет I/O-модулей), прогона на
исполнении тоже нет. Проверено ровно одно: **объявления и схемы компилируются
без ошибок**. Поведение на реальном ПЛК (и связь адресов с модулями) требует
профиля C и проверяется на железе — это записано и в `docs/04_ПЛАН_CPM.md`.

Адреса объявлены в отдельной GVL `GVL_IO_HW`, а не в самом блоке: объявление GVL
задаётся ТЕКСТОМ через scripting API (то есть это настоящее `AT`-объявление), а в
PLCopenXML адрес переменной структурно не передаётся — `AT` в текстовом дубле
интерфейса мог бы не попасть в компиляцию, и проба потеряла бы смысл.

### 14.6. Что осталось (честно)

1. Прогона на исполнении по-прежнему нет: конфигурации задач в проекте нет, то
   есть слой проверен компиляцией, сверкой по каждому POU и локальным `dryrun`.
2. `IN` из консольного канала (`Kind = 5`) НЕ ждёт символ: если символа нет,
   возвращается `FFh` (признак «нет данных», как у неназначенного порта). Ждать

### 14.8. Новые ограничения диалекта и окружения (этап 3.6)

1. **Поле структуры в массиве по ВЫЧИСЛЯЕМОМУ индексу работает** —
   `GVL_IO_Map.Map[Port].Kind` и запись `Map[Port].Fault := ...`. Это снимает
   вопрос «как в FBD сделать карту портов»: таблица дескрипторов делается прямо
   массивом структур, без теневых плоских массивов.
2. **`LIMIT` нужен не только для насыщения, но и для ИНДЕКСА**: номер порта
   ограничен типом (BYTE против массива 0..255), а номера каналов приходят из
   данных и потому проходят LIMIT. Иначе — выход за границу массива.
3. **Аналог считается в DINT**: 27648 x 255 не влезает в INT. `INT_TO_DINT` ->
   `MUL` -> `DIV` -> `LIMIT` -> `DINT_TO_BYTE` (проверено пробой).
4. **Обмен «процессор -> аппаратный слой» требует wait state**: аппаратный слой
   стоит НИЖЕ процессора в скане, значит ответ приходит на следующем скане. Это
   не ошибка схемы, а свойство порядка исполнения; PC и счётчик тактов на время
   ожидания замораживаются.
5. **Скриптовая проба адаптера C оказалась полезной**: `AT %IB0`-объявления
   Control Win V3 принимает и без модулей I/O. Но «компилируется» != «работает»:
   без модулей адреса ни с чем не связаны.
6. Окружение не изменилось: соседний проект по-прежнему снимает нашу сборку.
   Из трёх попыток подряд две были убиты на 16-й и 38-й секунде.

### 15.4. Латентные ошибки слоя этапов 3.2–3.6, найденные кодогенерацией

Все они были невидимы при разборе объявлений и проявились только при появлении

2. **Имена, совпадающие с ключевыми словами IEC**: `LD`, `S`, `R` (операторы IL),
   `ST`, `SEL`, `BIT`, `EXP`, `TO`, `DO`, `STEP`, `DATA`, `EQ/GE/GT/LE/LT/NE`.
   Симптом: `C9: Обнаружен недопустимый символ 'LD'/'S'/'st'/'to'/'Bit'/'Sel'/'exp'`.

## 16. Этап A5: локализация последней ошибки `C32 'BYTE' -> 'BOOL'`

### 16.1. Постановка

После снятия всех синтаксических ошибок (п. 15.4) осталась ровно одна:

```
Компиляция: Error: C32: Невозможно конвертировать тип 'BYTE' в тип 'BOOL'
Компиляция завершена -- 1 ошибок, 0 предупреждений : загрузка невозможна
```

`login()` падает на компиляции, поэтому симуляция не поднимается и прогона
тестов нет. **Главная трудность: headless-вывод печатает только код и текст
сообщения — без имени POU и номера сети**, тогда как GUI печатает
`POU (Network N)`. Поиск «на глаз» четырежды не дал результата, поэтому работа
разделилась на две независимые линии: (1) довести до конца статическую
проверку типов и (2) научиться локализовать ошибку компилятором.

### 16.2. ЧЕТЫРЕ СЛЕПЫЕ ЗОНЫ `tools/check_types.py` — найдены и закрыты

Проверка типов существовала с этапа 3, но **молча пропускала ровно те связи,
среди которых пряталась ошибка**. Все четыре дефекта были в самой проверке:

1. **Таблица глобалов не подключалась.** В `check_pou` стояло `env = {}`, и
   `env_all` (GVL_MEM/GVL_CPU/GVL_CPM/GVL_IO…) не накладывался. Любая ссылка на
   глобальную переменную разрешалась в `UNK`, а `compatible(UNK, …)` всегда
   истинна — то есть **все связи через GVL не проверялись вообще**.

2. **27 зависимостей ядра не проверялись изнутри.** Они использовались только
   как справочник типов входов/выходов, а их СОБСТВЕННЫЕ сети — нет. Именно в
   них выполнялось переименование `R->Rx`, `S->Sx`, `LD->LDx`. Теперь
   зависимости берутся из `pou_deps.make()` и проверяются наравне с прочими.

3. **Смесь двух систем имён.** Файлы `src/dep_fix/*.plcopenxml` УЖЕ
   переименованы, а объекты `Pou` из `GROUPS`/`pou_deps` — ещё нет. Прежний
   код грузил XML и ЗАТИРАЛ интерфейсы зависимостей переименованными именами;
   в итоге 5 связей (`FB_Reg16.LD`, `FB_Mux8x8.Sel`, `FB_Mux8x16.Sel`,
   `FB_CtrlUnit.S` во `FB_CPU8080_FULL`) объявлялись «пином не из интерфейса»,
   а все обращения к выводам зависимостей уходили в `UNK`. Теперь
   первоисточник (`pou_deps`) главнее, XML — только резерв.

4. **Квалификация по имени GVL.** В схемах есть записи `GVL_CPM.CPM_WE`,
   `GVL_HMI.Btn_Reset`, `GVL_IO.Tact_Busy`. Имя GVL — это НЕ переменная,
   поэтому такие выражения разрешались в `UNK`. Теперь каждый GVL
   регистрируется как СТРУКТУРА с полями, и разбор «имя.поле» идёт тем же
   кодом, что и для DUT.

Дополнительно исправлены два дефекта разбора объявлений (они давали **ложные**
срабатывания, из-за которых настоящую ошибку было легко потерять в шуме):

* **начальное значение попадало в тип**: в `GVL_TEST` есть `Mode : BYTE := 1;`,
  и типом становилось `"BYTE := 1"`. Такой «тип» не совпадал ни с одним
  элементом, объявлялся как `kind='fb'`, а `compatible()` для `kind='fb'`
  отвечает «несовместимо» — отсюда **18 ложных C32** в `TEST_8080`, `TEST_CPM`,
  `TEST_IO`. Теперь всё до первого `:=` отбрасывается;
* **массивы не разбирались вообще**: `Memory : ARRAY[0..65535] OF BYTE;` не
  подходил под прежний шаблон (в классе символов был исключён `[`), поэтому
  `ARRAY` всегда давал `UNK` и связи через память не проверялись;
* **разбор выражения переписан на последовательный**: прежний вариант
  разбирал `имя.поле` и `имя[индекс]` отдельными шаблонами и на составном
  `GVL_TEST.Tests[idx].Code[0]` (жадное `.*` внутри скобок) возвращал тип
  ЭЛЕМЕНТА массива — `ST_TestCase`. Это давало ещё **16 ложных C32**
  («приёмник BYTE <- ST_TestCase») в `TEST_8080`. Теперь выражение читается
  слева направо: имя, затем цепочка `.поле`, `.бит`, `[индекс]`
  (со балансировкой скобок), и тип преобразуется на каждом шаге.

**Инструменты проверки обзавелись измерением охвата** — иначе «0 ошибок» не
означает ничего. Печатается: сколько входов реально проверено, сколько
источников осталось `UNK`, сколько блоков неизвестного типа и сколько пинов не
из интерфейса (обе последние категории — «слепые зоны», раньше они молчали).

Текущий итог: **проверено 13 090 связей, `UNK` 348 (2.7 %), слепых зон 0,
находок 0.**

### 16.4. РЕШЕНИЕ: бисекция по ТЕЛАМ POU, а не удаление POU

Локализовать ошибку поручено самому компилятору. Ключевая идея — **у выбранных
POU оставлять ИНТЕРФЕЙС (все объявления) и убирать только СЕТИ**:

* проект остаётся **САМОСОГЛАСОВАННЫМ**: все типы на месте, ссылок на
  несуществующее нет, каскада `C0046/C77` не возникает;
* код внутри опустошённых POU не генерируется, поэтому их вклад в ошибку
  исчезает.

Именно этого не хватало двум прошлым попыткам бисекции: **удаление POU** ломало
ссылки, вызывающий не находил тип, кодогенерация для него пропускалась — и
искомая ошибка МАСКИРОВАЛАСЬ под каскадом `C0046`.

Обозначим `T(S)` = «ошибка C32 есть, если опустошить тела POU из S». Известно
`T(пусто) = истина`. Делим кандидатов `cur` на `A` и `B`:

```
T(A) = ложь   -> ошибка ВНУТРИ A  -> cur := A
T(A) = истина -> ошибки в A нет   -> cur := B
```

Так как ошибка ровно одна, после `log2(N)` сборок остаётся один POU.

Реализация:

* `gen_bisect2.py` — копия `gen_stage4.py`; список имён для опустошения берётся
  из переменной окружения `DSH_BISECT_EMPTY` (значение `*` = опустошить все);
* `tools/run_bisect.ps1` — автоматический цикл: шаг 0, бисекция, проверка
  найденного кандидата; журнал пишется в `C:\dsh8080\work\bisect_result.txt`.
  Каждая сборка — отдельный процесс CODESYS, при неполном прогоне (занятый
  мьютекс) попытка повторяется.

### 16.7. ПРИЧИНА ОШИБКИ C32 — НАЙДЕНА (пять уровней бисекции)

Ошибка локализована **самим компилятором**, шаг за шагом, пятью уровнями
бисекции (каждый уровень — отдельный скрипт, см. 16.4):

| Уровень | Что делили | Результат |
|---|---|---|
| 1 | тела 67 POU | `FB_CPU8080_FULL` |
| 2 | сети этого POU (33) | сеть 17 — «СЕТЬ 18 (ФАЗА 6). Флаги S/Z/P результата DAA» |
| 3 | элементы этой сети (55) | ошибка появляется, когда **читается выход** вызова `FB_ALU8` |
| 4 | сети `FB_ALU8` (17) | сеть 1 — «Признаки операции» |
| 5 | элементы сети 1 (12) | ошибка остаётся даже при **одном** элементе |

Пятый уровень дал решающий факт: **тело `FB_ALU8` ни при чём** (даже пустое, с
одним `<inVariable>`, ошибка сохраняется). Значит, виноват **сам вызов**.

**ГЛАВНАЯ ПРИЧИНА, ПОЧЕМУ ЭТО НЕ НАХОДИЛОСЬ ТАК ДОЛГО.** Тело зависимости
кодогенерируется **только если её кто-то ВЫЗЫВАЕТ**, а вызывалась `FB_ALU8`
ровно из одного POU — `FB_CPU8080_FULL`. Пока его тело опустошалось (а так
делали ВСЕ проверки и прошлые попытки бисекции), вызов становился «мёртвым»,
CODESYS его выбрасывал, и ошибка ИСЧЕЗАЛА. Отсюда ложный вывод «зависимости
в порядке». То же и внутри сети: при 5 элементах (вызов есть, выходы не
читаются) ошибки нет, при 6 (первый выход читается) — есть.

**СУТЬ ДЕФЕКТА.** В сети 17 вызов `FB_ALU8` объявлял **все шесть** выводов

```
[R, CY, AC, S, Z, P]
```

а читал **только три**: `S`, `Z`, `P` (4-й, 5-й и 6-й по объявлению). Импортёр
PLCopenXML сопоставляет выводы **ПОЗИЦИОННО**, поэтому прочитанные выводы
привязались к ПЕРВЫМ ТРЁМ объявленным:

```
daa_s (BOOL) <- Rx  (BYTE)   ->  C32 'BYTE' -> 'BOOL'   <- единственная ошибка
daa_z (BOOL) <- CY  (BOOL)   ->  молча, но НЕВЕРНО
daa_p (BOOL) <- AC  (BOOL)   ->  молча, но НЕВЕРНО
```

Компилятор сообщил ровно одну ошибку (про `daa_s`), и загрузка была невозможна.

**ДОКАЗАТЕЛЬСТВО (два одношаговых эксперимента).** При опустошённых 66 POU и
одной сети 17:

* `daa_s (BOOL) <- ualu.S` → **C32 'BYTE' -> 'BOOL'**;
* `daa_s (BOOL) <- ualu.Z` (тоже BOOL, но НЕ переименованный) → **C32**;
* `daa_r (BYTE) <- ualu.R` → **0 ошибок, «готово к загрузке»**.

То есть ошибку даёт чтение **любого BOOL-выхода** этого вызова.
Предположение «виновато переименование `S`→`Sx`» проверено и ОТВЕРГНУТО: не
переименованный `Z` ведёт себя так же.

**ПОЧЕМУ ДЕФЕКТ БЫЛ РОВНО ОДИН НА ВЕСЬ ПРОЕКТ.** Все остальные вызовы FB
читают **все** свои выводы **в порядке объявления** (`FB_UnpackByte` B0..B7,
`FB_PackByte` B, `FB_FullAdder` Sum/Cout, `FB_Rotate8` R/CY_Out, `FB_DAA`
R/AC_Out/CY_Out, `FB_UnpackWord` Lo/Hi) — там позиционное сопоставление
совпадает с именованным. Достаточно было **одного** вызова с подмножеством
выводов, чтобы весь проект не собирался.

### 16.8. ИСПРАВЛЕНИЕ — ОБЩЕЕ, А НЕ ТОЧЕЧНОЕ

Точечная правка одного вызова проблему снимала, но оставляла Class-дефект:
в проекте нашлось ещё **10** вызовов FB, читающих подмножество выводов не с
начала списка (`FB_CtrlUnit`, `FB_CPM_DirEngine`, `FB_COM_Loader`, `FB_IO_Read`,
`FB_IO_AnalogIn`). Они не давали ошибки только потому, что типы там совпали
позиционно, — то есть **могли молча считать не то, что написано**.

Поэтому правило введено в генератор. В `fbd_xml.Pou` добавлен метод
`_prune_outputs()`, который вызывается в `render()` **перед** `_expand_fanout()`
и оставляет в каждом вызове FB **ровно те выводы, которые читаются, и в том
порядке, в котором они читаются**:

```python
def render(self):
    self._prune_outputs()     # НОВОЕ: выравнивание списка выводов вызова
    self._expand_fanout()
```

Тогда и позиционное, и именованное сопоставление дают верный результат.

Проверка правила без CODESYS — **`tools/check_outpins.py`**: она вызывает
`p.render()` (чтобы увидеть уже усечённые списки) и сверяет порядок чтения с
объявленным. После правки: **0 мест**.

### 16.9. РЕЗУЛЬТАТ: ПРОЕКТ СОБИРАЕТСЯ С НУЛЁМ ОШИБОК И ЗАПУСКАЕТСЯ

## 17. ФАЗА B: ОТЛАДКА ПРОГОННОГО АВТОМАТА (почему ни один тест не выполнялся)

### 17.1. Постановка

После этапа A5 проект собирался с 0 ошибок и запускался в симуляции, но
**набор 8080 не выполнялся вообще**: `Pass_Cnt = 0`, `Fail_Cnt = 1170`,
фактический `PC` почти всегда был КОНСТАНТОЙ `03C3` (иногда `E003`, `FE03`)
вместо ожидаемых `0201`/`0203`, `A` оставался исходным. То есть процессор
**не выполнял тактов**, а автомат прогона помечал кейсы FAIL.

### 17.2. Метод: ПОСКАНОВЫЙ СЛЕД

Headless-компилятор не печатает ни имён, ни номеров сетей, поэтому пришлось
получить наблюдаемость. Инструмент — `gen_probe_run.py`: он открывает уже
собранный проект, логинится, запускает приложение и опрашивает набор
переменных с заданным периодом (файл `log/trace_run.log`).

Ключевой приём: **задача собирается с ЗАМЕДЛЕННЫМ интервалом**
(`DSH_S4_INTERVAL=T#200ms`). При обычных `T#2ms` прогон даёт 2500 сканов за 5 с,
и скрипт не успевает опрашивать; при 200 мс опрос попадает на каждый скан.
Пересборка для повторного снятия следа не нужна.

### 17.3. НАЙДЕННЫЕ ДЕФЕКТЫ (все подтверждены следом)

**1. `pou_cpu_io` ЗАТИРАЛ патч порта CP/M у PC — ГЛАВНАЯ ПРИЧИНА.**
`pou_cpu_cpm.make_cpu_cpm()` добавляет к входу `LD` счётчика команд запись от
CP/M: `pc.LD = OR(<загрузка от процессора>, cpm_pc_wr)`. Затем
`pou_cpu_io.make_cpu_io()`, ПАТЧ 2 (гашение записи PC на время wait state),
собирал `LD` ЗАНОВО из `OR(run_i, int_take)` и тем самым **вход `cpm_pc_wr`
выбрасывал**. Аналогичный патч для `SP` никто не перекрывал — поэтому `SP`
писался, а `PC` нет.
След подтвердил это прямо: в фазе PH_PC трап выставлял `CPM_WE=1, CPM_LD1=1,
CPM_Sel1=7, CPM_Data1=0F100h`, `Reg_SP` становился `0F200h`, а `Reg_PC`
оставался `0`.
Последствия: стартовая установка `PC := 0F100h` не доходила, процессор
исполнял нулевую страницу и уходил в BIOS (`E003`, `FE03`), автомат трапов
застревал в фазе TRAP без активного диспетчера и без квитанции `Func_Done`,
`CPU_Enable` навсегда становился FALSE — и ни один такт не выполнялся.

**2. `TEST_8080` ОБНУЛЯЛ порт CP/M, когда не владел процессором.**
В сети 5 при `own = FALSE` стояло `CPM_WE := FALSE`, `CPM_Sel1 := 0`,
`CPM_Data1 := 0` и т. д. Но `TEST_8080` идёт в задаче ПЕРВЫМ, а трап пишет порт
в `PLC_PRG_CPM` ПОЗЖЕ — значит выставленные трапом значения должны дожить до
вызова процессора в следующем скане, а тест стирал их в начале каждого скана.
Исправлено: не владея процессором, схема пишет обратно ТЕКУЩЕЕ значение.

**3. Фаза RUN длилась ровно один скан.**
Переход `RUN -> STOP` был безусловным, а такт внутри `FB_CPU8080_FULL` разрешён
условием `run = Enable AND NOT Halted`, где `Enable = CPU_Run AND CPU_Enable`,
а `CPU_Enable := f_wk` — признак того, что автомат трапов находится в фазе
WORK(8). Если скан фазы RUN не совпал с WORK, такт не выполнялся.
Исправлено: `tact` считает **РЕАЛЬНЫЕ** такты (по изменению `GVL_CPU.Step_Cnt`),
а `RUN -> STOP` происходит только когда набрано `c_tacts` таких тактов — ровно
то, ради чего в кейсах есть поле `MaxTacts`.

**4. Не было АРБИТРАЖА ПРОЦЕССОРА между тестом и слоем CP/M.**
Трап вызывался с `Enable := TRUE` безусловно, а `CCP` (точка входа `0F100h`
сама является ловушкой) занимает процессор непрерывно. Исправлено: на время
прогона набора 8080 (`Mode = 1` и набор не завершён) трап ОТКЛЮЧАЕТСЯ, а его
автомат принудительно удерживается в фазе WORK — иначе отключённый трап всё
равно выполнял стартовые записи PC/SP и выставлял `Trap_Active`.
Дополнительно `own` и `start_ok` смотрят на `GVL_CPM.Trap_Active`, а не на
номер фазы трапа.

**5. Автоматы TEST_CPM и TEST_IO не гейтились своим режимом.**
`Mode := 3` (TEST_CPM) и `Mode := 0` (TEST_IO) выставлялись без проверки, что
соответствующий набор реально работал, а их фазовые автоматы шли без паузы.
Из-за этого цепочка режимов `1 -> 2 -> 3 -> 0` проскакивала за первые сканы,
`Mode` оказывался `0`, и набор 8080 не запускался. Исправлено: пауза автомата
по своему режиму (`go` для TEST_CPM, `own` для TEST_IO) и гейт на запись `Mode`.

**6. ОНЛАЙН-СЕССИЯ СТАРТУЕТ СО ЗНАЧЕНИЙ, СОХРАНЁННЫХ В ПРОЕКТЕ.**
Прогон начинался не с инициализаторов объявлений, а с состояния ПРЕДЫДУЩЕГО
запуска (`Mode = 0`, `DoneCpm = TRUE`, `DoneIo = TRUE`, `Scans = 94`).
Исправлено: `run_online.py` перед прогоном сбрасывает состояние
(`GVL_TEST.Mode := 1`, `N_Cases := 199`, `Done* := FALSE`, счётчики := 0).
Способ записи проверен пробой `gen_api3.py`: у `OnlineApplication` **нет**
`write_value`; используется prepared-механизм —
`set_prepared_value(имя, значение_СТРОКОЙ)` + `write_prepared_values()`.

**7. Фаза автомата — это ЛОКАЛЬНАЯ переменная POU, и она тоже сохраняется.**
После сброса глобальных счётчиков автомат стартовал не с IDLE, а с той фазы,
на которой его застал прошлый запуск (в частности с HAND), из-за чего набор
объявлялся пройденным при `Idx = 0`. Исправлено: одноразовый сброс в FBD —
если `GVL_TEST.Scans = 0`, фаза принудительно ставится в IDLE.

### 17.4. ЧТО ЭТО ДАЛО

* `Reg_PC = 0F100h`, `Reg_SP = 0F200h` — **трап корректно загружает CCP**;
* **журнал консоли CP/M наполняется** (был 0 знаков) — консоль CP/M реально
  работает; одна проверка слоя CP/M перешла в PASS;
* прогон перестал быть «мгновенным»: `Idx` растёт по одному кейсу;
* ввод-вывод: 3 проверки PASS (чтение дискретного входа, инверсный канал,
  масштаб аналога из 27648 в 255).

### 17.5. ЧТО ОСТАЛОСЬ (следующий шаг фазы B)

Набор 8080 всё ещё не стартует: `Idx = 0`, `Pass_Cnt = 0`, `Fail_Cnt = 0`,
`Mode` останавливается на `2`. Значит, автомат `TEST_8080` доходит до фазы
HAND, не выполнив кейсов. Нужен поскановый след **с включённым сбросом**
(в `gen_probe_run.py` сброс пока не добавлен) — он покажет, на каком именно
переходе `IDLE -> LOAD -> ... -> HAND` теряется прогон.

## 18. ФАЗА B (продолжение): ПРОГОН ЗАРАБОТАЛ, 117/199 PASS

### 18.1. Найденные дефекты (в порядке обнаружения)

**1. `pou_cpu_io` ЗАТИРАЛ патч порта CP/M у PC.** ПАТЧ 2 собирал вход `LD`
счётчика команд заново из `OR(run_i, int_take)` и выбрасывал `cpm_pc_wr`,
добавленный ранее `pou_cpu_cpm`. Для `SP` такого перекрытия не было, поэтому
`SP` писался, а `PC` — нет. Следствие: `PC` не загружался в `0F100h`,
процессор уходил в BIOS, автомат трапов застревал в фазе TRAP без диспетчера
и без квитанции `Func_Done`, `CPU_Enable` навсегда FALSE — **ни одного такта**.
Исправлено: гейт накладывается на ТЕКУЩИЙ источник `LD`
(`AND(<прежний LD>, NOT(io_wait))`), а не собирается заново.

**2. `TEST_8080` обнулял порт CP/M, не владея процессором.** В сети 5 при
`own = FALSE` стояло `CPM_WE := FALSE`, `Sel1 := 0`, `Data1 := 0`. Но
`TEST_8080` идёт в задаче ПЕРВЫМ, а трап пишет порт ПОЗЖЕ — значения трапа
стирались до того, как процессор их увидит. Исправлено: писать обратно
ТЕКУЩЕЕ значение.

**3. Зеркальная полярность `SEL`.** `SEL(G, IN0, IN1)` возвращает **IN1 при
G = TRUE**. Два места были написаны наоборот:
* `CHAIN_MODE`: `SEL(f_hand, 2, Mode)` читалось как «если набор НЕ закончен,
  то 2» — `Mode` становился 2 сразу, `TEST_CPM` добивал до 3, набор 8080 не
  выполнялся ни разу. Правильно `SEL(f_hand, Mode, 2)`.
* Цепочки каналов/данных порта (сеть 5): `SEL(f1, 0, SEL(f2, 2, ...))` давало
  в фазе W1 последнее значение (8 = SP вместо 0 = A), то есть регистры
  писались не туда. Исправлено функцией `_first`, которая строит цепочку с
  конца и даёт «первое совпадение выигрывает».

**4. Фаза RUN выдавала ЛИШНИЙ такт.** `stop_now` вычисляется до обновления
`tact`, поэтому в скане перехода RUN -> STOP процессор был ещё включён.
Однобайтовая команда давала `PC = 0203` вместо `0201`. Промежуточный вариант
(счёт по `GVL_CPU.Step_Cnt`) дал `0202`, потому что признак отстаёт на скан:
процессор исполняется в `PLC_PRG_CPM` позже этой схемы. Итог:
`CPU_Run := f_run AND NOT stop_now`, а `tact` считает ВЫДАННЫЕ такты.

**5. Автоматы TEST_CPM и TEST_IO не гейтились своим режимом** и проскакивали
цепочку `1 -> 2 -> 3 -> 0` за первые сканы. Добавлены пауза по своему режиму и
гейт на запись `Mode`.

**6. Онлайн-сессия стартует со значений, СОХРАНЁННЫХ В ПРОЕКТЕ**, а не с
инициализаторов; ЛОКАЛЬНЫЕ переменные POU (`ph`, `idx`, `tact`) тоже
сохраняются. Поэтому введён явный сигнал `GVL_TEST.Reset`: схема сама ставит
`ph := IDLE`, `idx := 0`, `Mode := 1`, обнуляет счётчики и снимает сигнал в
конце того же скана.

**7. prepared-механизм применяет ОДНО значение за вызов.** Писать надо по
одному: `set_prepared_value` + `write_prepared_values` на каждую переменную,
иначе применяется только последняя.

**8. Порядок в генераторе MOV-кейсов.** Приёмник обнулялся ПОСЛЕ установки
источника, поэтому для `MOV A,A`, `MOV B,B`, ... значение источника терялось:
начальное `B = 00h`, ожидалось `B = 22h` — 8 кейсов не могли пройти никогда.
Исправлено: сначала приёмник, затем источник.

**9. Шаг экспорта XML валил сборку.** Выгрузка всего проекта в один XML
(~13 МБ) роняет CODESYS до сохранения, поэтому на диске не оставалось
проекта. Добавлено: сохранение проекта СРАЗУ после компиляции и переключатель
`DSH_S4_NO_EXPORT`.

### 18.2. Последние дефекты, которые это разблокировали

Раздел 17 описывал, почему набор 8080 не выполнялся. После его исправления

`done_gate` вычислялся как `hit AND (ph_next = 0)`, но `PH_INIT = 0`!
То есть CCP в начальной фазе (сброс буферов) немедленно сообщал «функция
выполнена», и трап возвращал управление, не дав прочитать строку.
Исправление (`pou_ccp.py`): квитанция только при возврате в 0 ИЗ фазы
разбора: `hit AND NOT(f_init) AND (ph_next = 0)`.

**3. Приоритет правил автомата CCP был инвертирован.**
`CHAIN` строит цепочку `SEL`, где КАЖДЫЙ следующий шаг перекрывает
предыдущий - приоритет у ПОСЛЕДНЕГО совпавшего правила. В таблице `TRANS`
условные переходы стояли ПОСЛЕ безусловных, поэтому условные подавляли
`always`, а сам `always` не срабатывал: CCP застревал в фазах 5 (CR) и
13 (ENDTOK). Исправление: правила группируются по фазе и сортируются так,
что безусловное правило оказывается ПЕРВЫМ (младшим по приоритету).

**4. Подача знаков в консоль не продвигалась.**
Последовательно найдено и исправлено:
  * `k` увеличивался при `NOT ConIn_Ready`, но эта же сеть в том же скане
    ВЫСТАВЛЯЛА `Ready` - замкнутый круг;
  * прирост по `Trap_Active` не работал: CCP живёт ВНУТРИ трапа;
  * `hold` обнулялся, пока `armed` был FALSE, - прирост не наступал никогда
    (замер: `Cpm_Typed = 0`, `ConIn_Char = 13` всё окно);
  * `k` писался в ТОЙ ЖЕ сети, где вычислялся тик, а `hold` - после: `k`
    видел старое значение. Исправление: `hold` (сеть 2), `k` (сеть 2Б),
    выдача знака `feed`/`ch` (сеть 2В) - три последовательные сети.

**5. Проверки набора срабатывали только при `t == T_END`.**
`ok3/ok5/ok6/ok7` фиксировались строго при `t = T_END` (3000), но набор
закрывается раньше (по `cpm_moved`), поэтому `t` до 3000 не доходил и
проверки оставались FAIL при реально напечатанном каталоге.
Исправление: условие фиксации - `done` (набор закрывается в этом скане).

**6. Проверка 0 требовала `A>` строго в начале кольцевого буфера.**
Журнал - кольцо на 256 байт; при 600+ знаках начало перезаписано, поэтому
`Con_Log[0] = 'A'` не выполнялось никогда, хотя «A>» печатается постоянно.
Исправление: поиск пары «A>» в ЛЮБОМ месте буфера (200 позиций через `ORL`).

**7. Проверка 7 требовала вызовов BIOS через ловушку.**
В этой реализации CCP печатает приглашение и каталог САМ, `Diag.BIOS_Cnt`
остаётся нулевым. Исправление: проверяется то, что характеризует слой -
`CCP_Cnt >= 1`, `Diag.Trap_Cnt >= 1`, `Con_Log_Len >= 4`.

**8. Сводные счётчики CP/M считались раньше записи результатов.**
Замер `gen_cpmcount.py` в ОДНОЙ точке времени: `Cpm_Res[0..7]` все TRUE,
а `Cpm_Pass = 4`. Причина: `ok0/ok5/ok6/ok7` взводятся в том же скане, где
взводится `done`, а CODESYS отдаёт в той же сети СТАРОЕ значение.
Исправление: подсчёт вынесен в ОТДЕЛЬНУЮ сеть 8 (после сети 7, где пишется
массив), а флаг `done_prev` взводится в сети 7.

**9. Окно набора CP/M было короче, чем нужно двум командам.**
`T_MIN = 1200` сканов хватало для `DIR`, но `TYPE README.TXT` не успевал -
проверка 6 (`содержимое README.TXT`) оставалась FAIL. Исправление:
`T_MIN = 3000`, `DWELL = 20` (20 сканов на знак).
