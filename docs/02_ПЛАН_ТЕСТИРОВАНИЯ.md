Статус: **утверждено к реализации**. Зафиксированные решения: базовое устройство — `CODESYS Control Win V3`
(Simulation Mode), набор команд — **расширенный**, распаковка битов — **маски и сдвиги**,

## 0. Подшаг 0 закрыт: рабочий базовый проект (проверено запуском)

**Проблема.** Поставляемые шаблоны (`Templates\Standard.project`, `Empty.project`) ссылаются на
устройство `PLCWinNT` версии 3.1.3.0, которого **нет** в репозитории данного CODESYS.
Следствие — при компиляции: `C188: Устройство не установлено в систему. Генерация кода невозможна`.
Дополнительно `projects.create()` создаёт пустой проект без устройства и без Application,
а `proj.add_device(...)` в API этой версии отсутствует.

**Решение (найдено в дампе API `system.dump_scripting_api()`).**
Интерфейс `IScriptProjectDeviceExtension` («Projects which can contain devices») предоставляет метод
`add`. Проверено фактически — проект создаётся, устройство добавляется, Application появляется сам:

```python
proj = projects.create(ROOT + u"/build/EMU8080.project")
proj.add(name=u"Device", type=4096, id=u"0000 0001", version=u"3.5.17.30")
app = proj.active_application          # -> PLCWinNT: Plc Logic: Application
```

Результат прогона:
```
[1] projects.create OK
[2] create_device_identification -> DeviceID(type=4096, Id='0000 0001', Version='3.5.17.30')
[3] add(name,type,id,version) -> OK
[4] TREE: Project Settings / __VisualizationStyle / Device
             └ Plc Logic └ Application
[5] active_application -> Application
[7] saved
```

**Установленные версии устройства 4096** (проверено по `C:\ProgramData\CODESYS\Devices\4096`):

| id | версия |
|---|---|
| `0000 0001` | 3.5.17.30 |
| `0000 0002` | 3.5.17.30 |
| `0000 0004` | 3.5.17.30 |
| `0000 0022` | 3.5.17.30 |
| `1628 0073/0082/0083/0084/0085` | 3.5.17.31 |

**Побочная находка (пригодится в Шаге 3).** В API этой версии есть метод **`proj.add(...)`** —
значит проект можно строить с нуля, а не «вырезать» содержимое из шаблона.
Также подтверждено: `proj.export_xml/import_xml` (PLCopenXML), `proj.export_native/import_native`,
`app.build()`, `device.set_simulation_mode(True)`, `online.login/start`.

**Эксплуатационная тонкость.** CODESYS — single-instance приложение: если предыдущий headless-процесс
не освободил мьютекс, следующий запуск молча завершается с кодом 1, не выполнив скрипт
(пустой stdout, пустой лог). Поэтому запуск скриптов делается через
`generator/tools/run_codesys.ps1`, который убивает хвостовые процессы, ждёт завершения
и повторяет попытку, пока лог не станет непустым.

## 0.1. Расширенный набор команд: карта покрытия тестами

Реализуем и тестируем **полный набор 8080** — 78 опкодов. Группировка по тестовым подмножествам:

| Подмножество | Команды | Группа тестов |
|---|---|---|
| **Пересылки** | `MOV r1,r2`, `MOV r,M`, `MOV M,r`, `MVI r,d`, `MVI M,d`, `LXI rp,d16`, `LDA a`, `STA a`, `LDAX rp`, `STAX rp`, `LHLD a`, `SHLD a`, `XCHG`, `XTHL`, `SPHL`, `PCHL` | 1 |
| **Арифметика 8 бит** | `ADD r`, `ADI d`, `ADC r`, `ACI d`, `SUB r`, `SUI d`, `SBB r`, `SBI d`, `INR r`, `DCR r` | 2, 3 |
| **Арифметика 16 бит** | `INX rp`, `DCX rp`, `DAD rp` | 2, 3 |
| **Логика** | `ANA r`, `ANI d`, `ORA r`, `ORI d`, `XRA r`, `XRI d`, `CMA`, `CMP r`, `CPI d`, `STC`, `CMC` | 2, 3 |
| **Сдвиги** | `RLC`, `RRC`, `RAL`, `RAR` | 3 |
| **Десятичная коррекция** | `DAA` | 3 |
| **Переходы** | `JMP a`, `JZ`, `JNZ`, `JC`, `JNC`, `JP`, `JM`, `JPE`, `JPO`, `PCHL` | 4 |
| **Вызовы/возвраты** | `CALL a`, `CZ`, `CNZ`, `CC`, `CNC`, `CP`, `CM`, `CPE`, `CPO`, `RET`, `RZ`, `RNZ`, `RC`, `RNC`, `RP`, `RM`, `RPE`, `RPO`, `RST n` | 4 |
| **Стек** | `PUSH rp`, `POP rp`, `PUSH PSW`, `POP PSW`, `XTHL` | 4 |
| **Управление** | `EI`, `DI`, `NOP`, `HLT` | 4 |

**Про `EI`/`DI`:** в эмуляторе без подсистемы прерываний они декодируются, но не производят
действий — тест проверяет, что **PC увеличился на 1 и состояние регистров не изменилось**
(это фиксируется в документации как сознательное упрощение, а не как недоделка).

**Про `RST n`:** тестируется как `CALL` по адресу `n*8` с той же работой со стеком.

## 1. Принцип: тесты — это данные, а не код



Тест-кейсы живут в массиве структур `GVL_TEST.Tests : ARRAY[0..N-1] OF ST_TestCase`.
Одна FBD-схема `TEST_8080` прогоняет их по очереди за один скан на тест.
Это даёт:
- добавление теста = добавление строки данных (ST разрешён для генерации тестовых данных);
- масштабирование до 300+ кейсов без разрастания схемы;
- ровно одну схему прогона, которую нужно отлаживать.

### 1.1. Структура тест-кейса

```iecst
TYPE ST_TestCase :
STRUCT
    Id        : WORD;                    // T-001 ... (номер для отчёта)
    Name      : STRING(48);              // краткое имя
    Group     : BYTE;                    // 1=пересылки 2=ALU 3=флаги 4=переходы/стек 5=память 6=программы 7=синхронизация
    (* --- программа, которую кладём в память --- *)
    Code      : ARRAY[0..7] OF BYTE;     // до 8 байт кода
    CodeLen   : BYTE;
    MemAddr   : WORD;                    // дополнительная ячейка данных
    MemVal    : BYTE;
    (* --- начальное состояние --- *)
    InitA, InitB, InitC, InitD, InitE, InitH, InitL : BYTE;
    InitSP    : WORD;
    InitPC    : WORD;
    InitPSW   : BYTE;
    (* --- ожидаемый результат --- *)
    ExpA, ExpB, ExpC, ExpD, ExpE, ExpH, ExpL : BYTE;
    ExpSP     : WORD;
    ExpPC     : WORD;
    ExpPSW    : BYTE;
    PSWMask   : BYTE;                    // 1 = этот флаг проверяем; 0 = "не должен измениться"
    CheckMem  : BOOL;
    ExpMemAddr: WORD;
    ExpMemVal : BYTE;
    (* --- управление прогоном --- *)
    MaxTacts  : WORD;                    // сколько тактов даём тесту
END_STRUCT
END_TYPE
```

**Раскладка PSW (совпадает с реальным 8080):**

| бит | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|---|---|---|---|
| | S | Z | 0 | AC | 0 | P | 1 | CY |

**Семантика `PSWMask`** (ключевой механизм всего плана), бит за битом:

| `PSWMask[i]` | Что проверяем для флага `i` |
|---|---|
| `1` | флаг должен стать равным `ExpPSW[i]` |
| `0` | флаг **не должен измениться**: должен остаться равным `InitPSW[i]` |

Биты 1, 3, 5 (константы 1/0/0) при сравнении игнорируются.

Так одной строкой покрывается требование «INR/DCR/INX/DCX/ANA/ORA/XRA/CMP не трогают
часть флагов» — самая частая ошибка студенческих эмуляторов. Маска `PSWMask = 00h`
означает «PSW должен остаться точно таким, каким был».

### 1.2. Схема прогона `TEST_8080` (FBD, 6 сетей)

| Сеть | Логика | Зачем именно так |
|---|---|---|
| 1 | `IF NOT Busy`: загрузка `Tests[Idx]` в память (`Code[]`, `MemVal`) и в регистры (`LD`) | Инициализация — до первого такта |
| 2 | `FB_CPU8080(Enable := Busy AND NOT Test_Done)` | Один скан = один такт |
| 3 | `Tact := Tact + 1`; `End := (Tact >= MaxTacts) OR Halted` | Ограничитель: зависший тест не вешает прогон |
| 4 | Снимок регистров и флагов → сравнение с `Exp*` (по `PSWMask`) → `Results[Idx]` | Проверка **один раз**, по завершении теста |
| 5 | `Idx := Idx + 1`; `Busy := FALSE`; при `Idx = N` → `Test_Done := TRUE` | Переход к следующему |
| 6 | `R_TRIG(Run)` — старт прогона и сброс `Idx`, `Results`, `Test_Done` | Повторный прогон = регрессия одной кнопкой |

Проверка «ожидание vs факт» строится на дереве `EQ` + `AND` (по маске). Результат:
`GVL_TEST.Results : ARRAY[0..N-1] OF BOOL`, диагностика: `GVL_TEST.Actual : ARRAY[0..N-1] OF ST_CpuState`.

### 1.3. Ручной отчёт

Скрипт `generator/report_tests.py` читает `Tests`, `Results`, `Actual` через online-доступ и
печатает таблицу:

```
| ID    | Тест                    | Ожидание             | Факт                 | Итог |
|-------|-------------------------|----------------------|----------------------|------|
| T-201 | ADD A,B переполнение CY | A=00 CY=1 Z=1 P=1    | A=00 CY=1 Z=1 P=1    | PASS |
| T-213 | INR A не трогает CY     | A=00 Z=1 CY=1        | A=00 Z=1 CY=0        | FAIL |
```

## 2. Группа 1 — пересылки и загрузка (T-001 … T-120)

Правило генерации: для команд с полем регистра тест генерируется **на все комбинации полей**,
это бесплатно (данные, не схема). Предусловие по умолчанию для всей группы:
`A=11 B=22 C=33 D=44 E=55 H=66 L=77`, `M[HL]=M[0066]=88`, `M[0100]=AA`, `SP=0700`, `PC=0000`.

| ID | Команда | Предусловие | Ожидание | Что ловим |
|---|---|---|---|---|
| T-001…T-064 | `MOV DDD,SSS` — **все 64 комбинации** | регистры по умолчанию | регистр DDD = значение SSS; при DDD=6 пишем в `M[HL]`; при SSS=6 читаем `M[HL]` | полный охват кодировки `01 DDD SSS`, включая `MOV M,M` (HLT-подобная) |
| T-065…T-072 | `MVI DDD,data` — все 8 | data=`5Ah` | регистр DDD=`5Ah`, `PC = PC0+2` | длина команды 2 байта |
| T-073 | `MVI M,data` | `M[HL]=00` | `M[HL]=5Ah`, `PC=PC0+2` | запись в память через HL |
| T-074…T-079 | `LXI rp,data16` (BC,DE,HL,SP) | — | B=hi, C=lo (и т. д.), `PC=PC0+3` | склейка H/L (**`FB_PackWord`**), длина 3 байта |
| T-080 | `LDA addr` | `M[0100]=AA` | A=AA, `PC=PC0+3` | два байта адреса, порядок lo→hi |
| T-081 | `STA addr` | A=55 | `M[0100]=55`, A=55 | A не портится |

| T-083 | `STAX D` | A=77 | `M[DE]=77` | — |
| T-084 | `LHLD addr` | `M[0100]=34`, `M[0101]=12` | L=34, H=12 | порядок lo/hi не перепутан |
| T-085 | `SHLD addr` | H=12, L=34 | `M[0100]=34`, `M[0101]=12` | обратная запись |
| T-086 | `XCHG` | D=12,E=34,H=56,L=78 | D=56,E=78,H=12,L=34 | парная перестановка |
| T-087 | `SPHL` | H=07, L=00 | SP=0700 | — |

| T-281…T-284 | `RZ/RNZ/RP/RM` | флаг | возврат или PC+1 | условные возвраты |
| T-285 | `PUSH B` | BC=1234, SP=0700 | `M[06FF]=12`, `M[06FE]=34`, SP=06FE | порядок B,C |
| T-286 | `POP D` | SP=06FE, `M[06FE]=34`, `M[06FF]=12` | D=12, E=34, SP=0700 | — |
| T-287 | `PUSH PSW` | PSW=D7 | `M[06FF]=D7` | упаковка флагов (**`FB_PackByte`**) |
| T-288 | `POP PSW` | `M[06FF]=D7` | PSW=D7 | распаковка флагов (**`FB_UnpackByte`**) |
| T-289 | `HLT` | — | PC и регистры неизменны на 10 следующих тактах | HLT реально останавливает такт |
| T-290 | `RET` при мусоре в стеке | SP=0700 | PC = `M[0701]:M[0700]`, без зависания | нет «залипания» |

## 7. Группа 6 — программы целиком (T-371 … T-420)

Полноценные программы, проверяющие связку «выборка → декод → ALU → запись → PC» на десятках тактов.

| ID | Программа | Ожидание |

## 8. Группа 7 — синхронизация и порядок фаз (T-421 … T-450)

Тесты, которые ловят именно **архитектурные** ошибки FBD: гонки, задержки на такт,
неверный порядок сетей. Это регрессионный «забор» вокруг Шага 4.

| ID | Что проверяем | Ожидание | Какую ошибку ловит |
|---|---|---|---|
| T-421 | `MOV A,A` | A не изменился | чтение операнда после записи результата |
| T-422 | `MOV B,A` затем `MOV A,B` (2 такта) | значения переставлены | потерю старого значения |
| T-423 | `ADD A,A` | A = 2·A | операнд A прочитан до записи |
| T-424 | `INR A` при A=FF | A=00, Z=1, CY не тронут | порядок «ALU → флаги → CY» |
| T-425 | `MVI A,5Ah` | PC=PC0+2, а не +1 | длину команды |
| T-426 | Цепочка `MOV`/`MVI`/`JMP` подряд (1/2/3 байта) | PC точно на границах команд | счётчик длины команды |
| T-427 | `JMP` на 2 байта вперёд | PC = цель, не цель+1 | повторный инкремент PC |
| T-428 | `XRA A` затем `JZ` | переход сработал на следующем такте | задержку обновления флагов |
| T-429 | Два одинаковых такта подряд | результат идентичен | зависимость от предыдущего скана |
| T-430 | Прогон всей программы дважды подряд без сброса | второй прогон даёт тот же результат | неочищенное состояние между прогонами |

## 10. Критерии приёмки

1. **100 % PASS** по всем группам — таблица отчёта без единого FAIL.
2. **Стабильность**: прогон повторяется дважды подряд с одинаковым результатом
   (ловим зависимость от начального состояния — тест T-430).
3. **Регрессия**: после каждой правки схемы прогоняется **весь** набор, а не только упавшая группа.
4. **Отчёт**: таблица «ID → тест → ожидание → факт → PASS/FAIL» выгружается в
   `report/test_report.md` и в консоль.
5. **Схема читаема**: `FB_CPU8080` — 7 подписанных сетей, каждый кастомный FB — на своей
   странице FBD, соединения между фазами через GVL, без «спагетти».
