# ЗАМЕТКИ ДЛЯ АГЕНТОВ, ДЕЛАЮЩИХ Z80 И 6502

Что из опыта эмулятора 8080 переносится напрямую, а что будет другим.
Читать вместе с 10_ОШИБКИ_И_РЕШЕНИЯ.md и 12_ШАБЛОНЫ_FBD.md.

---

## 1. ЧТО ПЕРЕНОСИТСЯ БЕЗ ИЗМЕНЕНИЙ

1. **Семантика SEL** (`SEL(G,IN0,IN1)` = IN1 при G) — та же ловушка.
2. **Запись в массив по вычисляемому индексу теряется** — та же ловушка.
3. **Тело FB без потреблённого выхода не генерируется** — та же ловушка.
4. **Задержка outvar/invar в один скан** — та же ловушка; холостые сканы
   нужны обязательно.
5. **Онлайн-сессия стартует с сохранённых значений**, локальные переменные
   сохраняются — нужен явный Reset.
6. **Поскайсовые защёлки** — единственный способ увидеть, что делал такт.
7. **Один такт = один скан**, счётчик тактов, `CPU_Run`, `fire`.
8. **Регистровый файл с двумя адресуемыми портами**, флаги отдельными
   разрешениями записи.
9. **Шина теста отдельно от шины процессора** (`Inj`).
10. **Фазы теста ≥ 4 сканов**, окна диапазоном.
11. **Старт системы**: выключить процессор → PC/SP → включить.
12. **Два прогона** для подтверждения результата.

## 2. Z80: ЧТО ДОБАВИТСЯ

### Регистры
- Пары AF, BC, DE, HL + **альтернативный набор** AF', BC', DE', HL'
  (`EX AF,AF'`, `EXX`) — это ещё 8 байт состояния и переключение.
- **IX, IY** — 16-битные индексные регистры; адресация `(IX+d)`, `(IY+d)`
  требует суммирования со знаком.
- **SP, PC** — как у 8080.
- **I, R** — регистр вектора прерываний и регистр обновления памяти
  (R инкрементируется на каждом M1!). Для тестов важно, для CP/M — нет.

### Флаги
- S, Z, H (аналог AC), P/V (**двойное назначение**: чётность для логики,
  переполнение для арифметики), N (вычитание — нужен для DAA), C.
- **DAA у Z80 зависит от N и H** — не как у 8080.
- Флаги после `BIT` (Z = инверсия бита, остальные не меняются).

### Команды
- Префиксы: `CB` (сдвиги/биты), `ED` (расширенные), `DD`/`FD` (IX/IY),
  комбинации `DD CB dd op`.
- **Декодер должен быть двухуровневым**: первый байт выбирает таблицу,
  префиксные — свою. Это ~1500 opcode-слотов; генерируйте таблицу скриптом,
  не вручную.
- Блочные команды (`LDIR`, `CPIR`, `INIR`, `OTIR`) — многотактовые, требуют
  состояния между тактами (флаги P/V и сам повтор).
- `IN r,(C)` / `OUT (C),r` — порт задаётся парой BC, а не отдельным байтом.

### I/O
- **Порты 16-битные** (адрес на шине A0..A15), младший байт = номер,
  старший = в `B`. У нас порт был 8-битным — придётся расширить.
- `IN A,(n)` и `OUT (n),A` — только младший байт адреса, старший = A.

### Прерывания
- Три режима (IM 0/1/2), NMI, векторы. Для CP/M не нужны, для тестов — да.

## 3. 6502: ЧТО БУДЕТ САМЫМ СЛОЖНЫМ

### Адресация — главный риск
У 6502 почти всё адресуется ВЫЧИСЛЯЕМЫМИ адресами:
- Zero page (`$nn`) — 256 байт, активно используется;
- `($nn,X)`, `($nn),Y` — косвенная через нулевую страницу;
- absolute, absolute,X/Y, relative (ветвления ±127).

**Прямое следствие:** правило «запись по вычисляемому индексу теряется»
становится КРИТИЧНЫМ. У 8080 мы обошли его константными цепочками на 9
адресов; для 6502 так нельзя.

**Рекомендация:** с самого начала сделать блок памяти с входом `Addr`
(аналог `FB_Memory64K`), проверить его запись ОБРАТНЫМ ЧТЕНИЕМ, и только
потом строить ядро. Если блок не пишет — делать 256 присваиваний на страницу
(страниц 256 → 65536 присваиваний невозможно; нужно искать рабочий способ
записи через блок).

### Регистры
- A, X, Y (8 бит), SP (8 бит, страница `$01`), PC (16 бит), P (флаги).
- Нет регистровых пар — всё через память/нулевую страницу.

### Флаги P
- N, V, B (break), D (decimal), I, Z, C.
- **D (десятичный режим)** меняет поведение ADC/SBC — нужна отдельная ветка.
- **B (break)** — зависит от того, как нажата/не нажата команда `BRK`
  (при `PHP`/`IRQ` разное). Частая причина расхождений.
- Ветвления (`BEQ`, `BCS`, ...) — relative, ±127 от PC+2.

### Такты
- У 6502 такт = цикл шины: чтение/запись по адресу. Многие команды имеют
  «лишний цикл» при пересечении страницы (`abs,X` при переносе).
- Для эмулятора это значит: **шина должна уметь «сделать цикл чтения по
  адресу» и «цикл записи по адресу»** — а не только «взять операнд».
- Прерывания: NMI (вектор `$FFFA`), RESET (`$FFFC`), IRQ (`$FFFE`) —
  последовательность из 7 тактов (толкание PC и P).

### Прочее
- `JMP ($xxFF)` — известный баг 6502 (берёт старший байт из `$xx00`).
  Если делаете точный эмулятор — воспроизведите.
- Decimal mode: для CP/M-подобной ОС (например, для 6502-монитора) может
  не понадобиться, но тесты на флаги будут.

## 4. ОБЩАЯ АРХИТЕКТУРА (рекомендуемая)

```
СЕТЬ 1   выборка IR = Memory[PC]
СЕТЬ 2   декодер (класс, длина, поля)     <- таблица, сгенерированная скриптом
СЕТЬ 3   регистровый файл (два порта)
СЕТЬ 4   выбор адреса чтения (по коду)
СЕТЬ 5   чтение памяти (блок с входом Addr)
СЕТЬ 6   выбор операнда (регистр/память/непосредственный)
СЕТЬ 7   АЛУ (R, флаги)
СЕТЬ 8   выбор адреса записи, данные, разрешения
СЕТЬ 9   запись в регистры
СЕТЬ 10  запись в память
СЕТЬ 11  следующий PC (переходы, вызовы, возвраты)
СЕТЬ 12  флаги (раздельные LD)
СЕТЬ 13  счётчик тактов, ожидание I/O
```

Порядок сетей = порядок потока данных. Всё, что нужно «в этом же такте»,
должно быть посчитано до потребителя; помнить про задержку в скан.

## 5. ПЛАН РАБОТЫ (порядок, который сработал)

1. **Декодер + таблица тестов** (MOV/регистры) — 50–100 кейсов.
2. **АЛУ + флаги** — по группам, с масками.
3. **Память** (проверить запись!), стек.
4. **Переходы/вызовы/возвраты**.
5. **Прерывания**.
6. **I/O** (отдельная шина + инъекция).
7. **ОС/монитор** (старт, консоль, дисковые вызовы).
8. **Отчёт**: таблица результатов, два прогона.

Не начинать с ОС. Не начинать с I/O. Ядро должно быть 100 % до обвязки.

## 6. ОЦЕНКА ТРУДОЁМКОСТИ (по опыту 8080)

| Часть | На 8080 | Ожидание Z80 | Ожидание 6502 |
|---|---|---|---|
| Декодер | 256 opcode | ~1500 слотов, префиксы | 256, проще |
| Адресация | простая | средняя | сложная (косвенная) |
| Флаги | простые | сложные (N, P/V) | средние (D, B) |
| Память | 64 КБ через блок | то же | то же |
| I/O | 8-битные порты | 16-битные порты | memory-mapped |
| ОС | CP/M (CCP/BDOS/BIOS) | CP/M (то же) | свой монитор |

**Главный вывод:** больше всего времени уходит не на команды, а на
«молчаливые» дефекты CODESYS (см. каталог). Заложите наблюдаемость и
холостые сканы с первого дня — это сэкономит основную часть времени.
