# МЕТОДИКА ОТЛАДКИ CODESYS-ЭМУЛЯТОРА

Практическое пособие: как искать дефекты, которых не видно в коде.
Написано по опыту доведения эмулятора 8080 с 0 до 199/199 кейсов.
Применимо к Z80/6502 без изменений.

---

## 1. ГЛАВНЫЙ ПРИНЦИП

**В CODESYS-эмуляторе почти все дефекты «молчаливые»: компиляция чистая,
схема выглядит правильно, но результат неверный.**

Единственный надёжный путь: **наблюдаемость**. Схема должна уметь рассказать,
что она делала, — иначе отладка превращается в угадывание.

Правило: *сначала инструмент, потом исправление.* В нашем проекте на каждый
дефект сначала ставилась защёлка, и только потом правился код.

## 2. ЦИКЛ СБОРКИ: СДЕЛАТЬ ЕГО БЫСТРЫМ

Полный цикл (сборка + прогон + отчёт) занимал ~490 с. После настройки — 45 с.

**Что нужно:**
```powershell
$env:DSH_S4_NO_EXPORT='1'   # не экспортировать проект в XML (13 МБ валит CODESYS)
$env:DSH_S4_WAIT='200'      # сколько секунд ждать прогона
$env:DSH_S4_TAIL='8'        # сколько строк лога показывать
$env:DSH_S4_SETTLE='10'     # холостых сканов на такт (см. п. 5)
& .\tools\run_stage4.ps1 -Script .\gen_stage4.py -MaxAttempts 3 -RunTimeoutSec 1800 -QuietSec 4
```

**Правила:**
- НЕ использовать `-NoSrcCopy` (иначе работает старая копия исходников).
- Имя лога должно совпадать с именем скрипта.
- CODESYS однопользовательский: перед сборкой убедиться, что никто не
  запускает соседний проект (или заморозить чужие процессы через
  `quiet_build.ps1`).

**Проверки перед сборкой (секунды, экономят минуты):**
```powershell
python -c "import ast,io; ast.parse(io.open('gen_stage4.py',encoding='utf-8').read())"
python -X utf8 tools\check_types.py     # типы выражений в схемах
python -X utf8 tools\check_outpins.py   # непривязанные выводы
```

## 3. ЗАЩЁЛКИ (LATCH) — ОСНОВНОЙ ИНСТРУМЕНТ

**Проблема.** Поля декодера/управления живут ОДИН скан. Внешний опрос
(скрипт CODESYS) читает раз в ~0.3 с и почти всегда попадает между тактами:
за 6 секунд удалось поймать 2 сэмпла.

**Решение.** Латчить внутри схемы в МАССИВ по индексу кейса/фазы, а потом
прочитать массив.

### Шаблон: массив диагностики на кейс

```
GVL_TEST.ActIR   : ARRAY[0..198] OF BYTE;    (* опкод последнего такта *)
GVL_TEST.ActCls  : ARRAY[0..198] OF BYTE;    (* класс операции *)
GVL_TEST.ActRP   : ARRAY[0..198] OF BYTE;    (* код пары *)
GVL_TEST.ActAddr : ARRAY[0..198] OF WORD;    (* эффективный адрес *)
```

В схеме теста:
```
ActIR[idx]  := IF(f_run, GVL_CPU.Bus_IR,  ActIR[idx])
ActCls[idx] := IF(f_run, GVL_CPU.C_Class, ActCls[idx])
ActAddr[idx]:= IF(f_run, GVL_CPU.Bus_Addr, ActAddr[idx])
```

**Что это дало.** Именно так найдено: `LXI` декодируется верно, но не пишет
младший байт; `ADD M` не пишет A; адрес перехода собирается из прошлой
позиции PC (`C311h` вместо `0300h`).

### Шаблон: счётчики событий

Когда нужно узнать не значение, а ФАКТ события:
```
GVL_IO.Dbg_Scan : UDINT   (* сколько раз блок вызван — безусловно *)
GVL_IO.Dbg_Req  : UDINT   (* сканов с Req = TRUE *)
GVL_IO.Dbg_Rd   : UDINT   (* срабатываний rd_ok *)
```

**Что это дало.** `Dbg_Scan = 15 506` → блок исполняется; `Dbg_Req = 0` →
запрос до него не доходит. Дальше причина нашлась за один опыт.

### Шаблон: метки сканов (сдвиг фаз)

```
Dbg_N  : UDINT   (* общий счётчик сканов *)
Dbg_SD : UDINT   (* значение Dbg_N в момент события A *)
Dbg_SR : UDINT   (* значение Dbg_N в момент события B *)
```
Разница показала: диспетчер отвечает на скане 4820, ядро завершает такт на
4822 — ровно два скана, и байт между ними уже обнулён.

### Шаблон: «что видит конкретный потребитель»

Когда непонятно, чей запрос обрабатывается:
```
cpu_rd = AND(ready, NOT(GVL_IO.Inj), ad_en)   (* запрос процессора, не теста *)
Dbg_CRd := IF(cpu_rd, ad_rdata, Dbg_CRd)
```
Так выяснилось, что на запросе процессора порт = 0 (а не 10h), потому что
процессор стартовал в первом же скане фазы, когда операнд ещё не дошёл.

## 4. ПРАВИЛО ОДНОГО ИЗМЕНЕНИЯ

Одна гипотеза → одно изменение → одна сборка → замер → вывод.

При регрессе — немедленный откат (у нас было три таких: удержание RData,
разнесение загрузки A, блок журнала консоли). Каждый откат возвращал
известное состояние, и это важнее «красоты» кода.

## 5. ХОЛОСТЫЕ СКАНЫ УСТАНОВКИ КОНВЕЙЕРА

**Проблема.** Значение из `outvar` видно `invar`-у только через скан. При
одном такте на скан многотактовые команды читают операнд от прошлой позиции
PC.

**Решение.** Между тактами держать процессор выключенным `SETTLE` сканов:
```
settle := IF(f_run, IF(GE(settle, SETTLE), 0, settle+1), 0)
fire   := AND(f_run, GE(settle, SETTLE))
CPU_Run := IF(own, fire, CPU_Run)
tact   := IF(f_run, IF(fire, tact+1, tact), 0)
```

**Что это дало.** +13 кейсов сразу; все многотактовые программы (циклы,
переходы, стек) начали считать верно.

**Цена.** Прогон удлиняется в SETTLE раз (у нас 10 → ~40 с на весь набор).
Это дешевле, чем переделка ядра.

**Для Z80/6502.** Обязательно: там такты длиннее и операнды читаются на
разных фазах.

## 6. ДИАГНОСТИКА ПО ФАЗАМ

Тест — это автомат фаз. Часто дефект в том, что фаза не выполняется или
выполняется не в том порядке.

**Приёмы:**
- латч «было ли событие за прогон»: `Dbg := IF(cond, TRUE, Dbg)`;
- латч максимума: `Dbg := IF(x > Dbg, x, Dbg)`;
- счётчик сканов в фазе: `sc2 := IF(ph <> ph_prev, INT#1, sc2+1)`;
- окно фазы задавать ДИАПАЗОНОМ (`GE(ph,A) AND LE(ph,B)`), а не двумя
  флагами — у флагов задержка в скан.

**Что это дало.** Watchdog: `Dbg_TB = TRUE` (признак был), максимум
`Busy_Scans = 5`, предел 100 → искать в пределе (карта портов перезаписывала).

## 7. ПРОВЕРКА ГРАНИЦ СЧЁТЧИКОВ

Набор тестов не заканчивался (`Done = FALSE`), а PASS рос до 1538.
Причина: переход требовал `idx >= n`, а счётчик стоит на `n-1`.

**Правило.** Для любого счётчика нарисовать таблицу: начальное значение,
условие инкремента, условие завершения, что происходит на границе. Пограничные
условия (`idx+1 < n` против `idx >= n`) проверять отдельным кейсом.

## 8. СНАЧАЛА «ИСПОЛНЯЕТСЯ ЛИ», ПОТОМ «ПРАВИЛЬНО ЛИ»

Порядок вопросов при дефекте:
1. Блок вообще вызывается? (безусловный счётчик)
2. Его входы приходят? (защёлки входов)
3. Его выход потребляется? (тело FB генерируется только тогда)
4. Выход правильный? (защёлка выхода)

Три из четырёх «поломок» у нас были не про логику, а про то, что блок не
исполнялся или его выход не читался.

## 10. ЧТО ЧИТАТЬ В ОТЧЁТЕ

Отчёт (генерируется скриптом) содержит:
- таблицу кейсов с ожиданием и фактом;
- состояние GVL после прогона (PC, A, PSW, счётчики CCP/BDOS/BIOS);
- результаты проверок I/O.

**Важно:** достоверный итог — по массиву `Results[]`; счётчики PASS/FAIL в
схеме могут врать (граничные условия). Дублирующие строки из отчёта лучше
убрать.

## 11. КАК ЧИТАТЬ ПОДОЗРИТЕЛЬНЫЕ ПРИЗНАКИ

| Признак | Вероятная причина |
|---|---|
| все кейсы одного класса падают одинаково | не пишется регистр/пара (нет разрешения записи) |
| проходят однотактовые, падают многотактовые | задержка outvar/invar (нужны холостые сканы) |
| значение «на единицу» не то | инвертированная полярность SEL |
| чтение работает, запись нет | запись по вычисляемому индексу |
| блок есть, эффекта нет | тело FB не сгенерировано (выход не потреблён) |
| после перезапуска всё сломано | онлайн-сессия стартует с сохранённых значений |
| счётчик всегда 0 | запись в поле структуры/массив по вычисляемому индексу |
| сработало один раз и замерло | одноразовая инициализация / залипший флаг |

## 12. ШАБЛОН ПРОБЫ (Python, скриптовый движок CODESYS)

```python
proj = scriptengine.projects.open(PROJ)
app  = proj.active_application
oa   = scriptengine.online.create_online_application(app)
oa.login(scriptengine.OnlineChangeOption.Never, False)
oa.start()
oa.set_prepared_value(u"GVL_TEST.Reset", u"TRUE")   # сброс состояния
oa.write_prepared_values()
time.sleep(20)
# ... чтение значений ...
oa.read_values([...])        # пакетное чтение
oa.stop(); oa.logout()
```

**Подводные камни:**
- `write_value` НЕТ; только `set_prepared_value` + `write_prepared_values`,
  и пакетная запись применяет лишь последнее значение — писать по одному.
- значения приходят с префиксом (`INT#27`, `BYTE#16#5A`) — нужен парсер.
- `app.name` может бросить `AttributeError`.
- перед `login` убедиться, что сборка дала 0 ошибок (иначе «Логин не выполнен»).

## 13. ПОРЯДОК РАБОТЫ НАД ЭМУЛЯТОРОМ (рекомендация)

1. **Ядро без I/O и без CP/M.** Тестовая таблица кейсов + отчёт.
2. **Наблюдаемость сразу**: массивы `ActIR/ActCls/ActAddr` с первого дня.
3. **Холостые сканы** заложить до первых тестов — иначе будете ловить
   «странные» ошибки операндов.
4. **Память**: чтение и запись проверить отдельно (запись через константные
   цепочки или через блок с входом Address).
5. **I/O**: отдельный бит инъекции от теста; окно фаз диапазоном.
6. **CP/M / монитор / ОС**: старт системы делать идемпотентным и явным
   (выключить процессор → PC/SP → включить).
7. **Тестовые данные** проверять на эталонной таблице: они врут не реже схемы.
8. **Два прогона** перед выводами.
