**Важно про каскады.** `C0046`/`C77` — почти всегда следствие того, что
какой-то POU **не импортировался**. Компилятор честно говорит «не знаю такого
типа» про весь подграф. Не ищите 80 ошибок: найдите один не вставший POU.

## 3.2. `C32` — как разбирать (наш главный враг)

Первое, что надо понять: `C32` почти никогда не означает, что вы ошиблись в
типах. В трёх наших случаях это было:

1. **Позиционное сопоставление выводов FB** (см. 02, п. 2.8). Признак: ошибка
   ровно одна, повторяется при изменении схемы, но не уходит.
2. **Смешение BOOL и числового типа** в одном блоке `AND/OR/XOR/SEL`.
   Признак: `BYTE -> BOOL` или `BOOL -> BYTE` на входе `IN1/IN2`.
3. **Ложная тревога собственной проверки** — `WORD+BYTE`, `GE(INT,WORD)`,
   `SEL(0, BYTE)` компилируются нормально.

**Порядок разбора:**

```python
# 1. есть ли ошибка на самом деле - смотрим "Компиляция завершена"
# 2. если есть - ищем бисекцией по телам POU (файл 04)
# 3. найдя POU - смотрим вызовы FB в нём: объявлены ли ЛИШНИЕ выводы
# 4. смотрим, нет ли BOOL рядом с BYTE в одном AND/OR/XOR/SEL
```

## 3.3. Почему headless-компилятор молчит о месте ошибки

```
Компиляция: Error: C32: Невозможно конвертировать тип 'BYTE' в тип 'BOOL'
```

Только код и текст. GUI печатает `POU (Network N)`, headless — нет.
API (`system.get_messages()`) содержит **сообщения самого скрипта**, а не
компилятора — проверено. Поэтому единственный способ локализации — бисекция
компилятором (файл 04).

## 3.4. Приоритет правил в `CHAIN`/`SEL` — ИНВЕРТИРОВАН

Соберём цепочку:

```python
def CHAIN(n, acc, steps):
    for cond, val in steps:
        acc = SEL(n, cond, acc, val)   # каждый следующий ПЕРЕКРЫВАЕТ предыдущий
    return acc
```

`SEL(G, IN0, IN1)` возвращает `IN1` при `G = TRUE`. Значит **приоритет у
ПОСЛЕДНЕГО элемента списка**, а не у первого.

**Симптом:** автомат застревает в одной фазе; задуманный безусловный переход
не срабатывает, а срабатывает последнее условное правило.

У нас таблица переходов была написана «естественно»:

```python
(PH_ENDTOK, "always",  PH_TAILINI),   # кажется: безусловный - первым
(PH_ENDTOK, "tok_p0",  PH_SKIP),
(PH_ENDTOK, "only_arg", "ret"),
```

Побеждало `only_arg`, а `always` не срабатывало **никогда** — CCP застревал в
фазе 13.

**Решение:** группировать правила по фазе и внутри группы ставить безусловное
**первым** (то есть младшим по приоритету):

```python
_alw = [x for x in grp if x[0] == "always"]
_cnd = [x for x in grp if x[0] != "always"]
for flag, tgt in _alw + _cnd:
    order.append((ph, flag, tgt))
```

**Проверка:** напишите маленький скрипт, который печатает итоговый порядок для
каждой фазы и «победителя» при всех истинных условиях.

## 3.5. Защёлка «готово» срабатывала в ПЕРВОЙ же фазе

`done_gate = hit AND (ph_next = 0)` — и `PH_INIT = 0`. То есть CCP в начальной
фазе (сброс буферов) немедленно сообщал «функция выполнена», и трап возвращал
управление, не дав прочитать строку.

**Решение:** требовать, чтобы фаза СМЕНИЛАСЬ, а не просто стала нулём:

```python
done_gate = hit AND NOT(f_init) AND (ph_next = 0)
```

**Общее правило:** если фаза 0 — «начало», никогда не проверяйте `next = 0`
как признак завершения. Заведите отдельную конечную фазу или флаг.

## 3.6. Устаревшие значения в «умных» проверках

Наши проверки требовали `t == T_END` (например, `t = 3000`). Набор при этом
закрывался **раньше** (по факту выполнения команды), и `t` до 3000 не доходил —
проверки оставались `FAIL` при реально напечатанном каталоге.

**Решение:** фиксировать результат по **факту** («набор закрывается в этом
скане»), а не по номеру скана. Номер скана — хрупкая привязка к таймингам.
