# 02. ДИАЛЕКТ FBD: ЧТО CODESYS ДЕЛАЕТ МОЛЧА

Самый дорогой файл конспекта. Здесь собраны случаи, когда **нет ни ошибки, ни
предупреждения**, а схема работает не так или исчезает целиком. Каждый пункт
подтверждён экспериментом.

## 2.1. FAN-OUT УБИВАЕТ POU ЦЕЛИКОМ (грабли №1)

**Симптом:** POU импортируется без ошибки, но в проекте его нет; или есть, но
пустой. Компилятор молчит.

**Причина:** если **любой** выход (входная переменная ИЛИ выход блока) питает
больше одного входа, CODESYS 3.5 SP17 выбрасывает POU.

**Проверено бисекцией:** POU с fan-out теряется; тот же POU без fan-out —
на месте. Межсетевые ссылки при этом работают.

**Решение — разворачивать граф в дерево.** Каждый выход используется ровно
один раз; для каждого лишнего использования создаётся **копия элемента вместе
со всей его входной ветвью**, и вставляется перед потребителем:

```python
def _expand_fanout(self):
    all_items = []
    for net in self.networks:
        all_items.extend(net._items)
    by_id = dict([(it[1], it) for it in all_items])

    def sources(it):
        if it[0] == u"invar":  return []
        if it[0] == u"outvar": return [_src(it[3])]
        return [_src(s) for _, s in it[3]]

    uses = {}
    for it in all_items:
        for s in sources(it):
            k = (s.eid, s.pin)
            uses[k] = uses.get(k, 0) + 1
    if not uses or max(uses.values()) <= 1:
        return                      # fan-out нет - ничего не делаем
    ...                             # иначе клонируем ветви
```

**Считать надо по паре (элемент, ИМЯ ВЫВОДА) и по ВСЕМУ POU**, а не по сети:
разные выводы одного блока — разные источники, а межсетевые ссылки как раз и
создают fan-out.

**Отдельно:** вызов пользовательского FB **размножать нельзя** — экземпляр
один. Если выход вызова FB разветвляется, это ошибка проектирования: проведите
сигнал через переменную POU (защёлкните его `outvar` и читайте `invar`).

## 2.2. СВЯЗЬ «ВЫХОД ВЫЗОВА FB → ВХОД БЛОКА» ТЕРЯЕТСЯ

**Симптом:** схема выглядит правильно, но вход блока оказывается пустым;
кодогенерация падает с `C23: Для 'AND' необходимо как минимум '2' операндов`
или считает не то.

**Причина:** связь напрямую от выхода вызова FB к входу другого блока в той же
сети импортёр теряет.

**Правило (железное):** выход вызова FB **немедленно защёлкивать** в
переменную POU, а дальше использовать переменную.

```python
# ПЛОХО: al.out(u"CY") идёт прямо в другой блок
n.block(u"AND", [(u"IN1", al.out(u"CY")), (u"IN2", x)], ...)

# ХОРОШО:
n.outvar(u"alu_cy", al.out(u"CY"))       # защёлкнули
n.block(u"AND", [(u"IN1", I(n, u"alu_cy")), (u"IN2", x)], ...)
```

Мы добавили помощник:

```python
def latch(n, name, src):
    n.outvar(name, src)      # один outvar
    return I(n, name)        # и один invar для дальнейшего использования
```

## 2.3. ЧТЕНИЕ ВЫХОДА ВЫЗОВА FB ИЗ ДРУГОЙ СЕТИ ВЕШАЕТ ИМПОРТ

Ещё строже: попытка прочитать `block.out(...)` в **последующей сети**
приводила к зависанию импорта (процесс жив, скрипт не движется).

**Правило:** выход вызова FB читается только в той же сети, где вызов, и
только после защёлкивания (см. 2.2).

## 2.4. ЗАПИСЬ В МАССИВ ПО ВЫЧИСЛЯЕМОМУ ИНДЕКСУ ТЕРЯЕТСЯ

**Симптом:** `Log[i] := ch` не пишется; при этом `LogLen := LogLen + 1`
работает.

**Причина:** импортёр теряет запись по индексу-выражению.

**Решение:** писать по **константным** индексам, а выбор элемента делать
сравнением, разложив массив на «банки»:

```python
for bank in range(LOG_SIZE // 32):
    nx = p.network(u"журнал, индексы %d..%d" % (bank*32, bank*32+31))
    idx = MOD(nx, ADD(nx, I(nx, u"LogLen"), I(nx, INT#(LOG_SIZE-1))),
              I(nx, INT#LOG_SIZE))
    for k in range(bank*32, bank*32+32):
        e = u"GVL.Con_Log[%d]" % k
        hit = AND(nx, gate, EQ(nx, idx, I(nx, INT#k)))
        nx.outvar(e, SEL(nx, hit, I(nx, e), I(nx, u"out_ch")))
```

Цена: 32 сети на каждые 1024 байта буфера. У нас журнал был 256 байт (8 банков).

**Про размер буфера:** 256 байт **не хватило** — вывод команды `DIR` (каталог
из 4 записей по 32 байта плюс приглашения) затирал начало журнала. Берите с
запасом, но помните, что размер линейно увеличивает число сетей и время
сборки: у нас 1024 байта дали 24 лишние сети и импорт застрял на 8+ минут.

## 2.5. ЧТЕНИЕ GVL-ЯЧЕЙКИ В ТОЙ ЖЕ СЕТИ, ГДЕ ОНА ПИШЕТСЯ → СТАРОЕ ЗНАЧЕНИЕ

**Симптом:** проверка «сумма результатов» показывает 4 при фактических 8.

**Причина:** в пределах одной сети CODESYS отдаёт СТАРОЕ значение ячейки, даже
если запись стоит выше в той же сети.

**Решение:** разносить запись и чтение по **разным сетям**, причём читающая
сеть должна идти **после** пишущей.

У нас это вылилось в правило: `ok0..ok7` фиксируются в сетях 4–6, массив
`Cpm_Res[]` пишется в сети 7, сумма считается в сети 8.

**Тот же эффект с локальными переменными.** Переменная, вычисляемая в сети N,
при чтении в той же сети даёт старое значение. Если нужен результат «в этом же
скане» — выносите в отдельную сеть.

## 2.6. ПУСТОЙ `<interface>` → POU ИСЧЕЗАЕТ МОЛЧА

POU без объявленных переменных (пустой блок `<interface>`) импортируется без
ошибки и **не появляется в проекте**.

**Правило:** у каждого POU должна быть хотя бы одна переменная. Если POU
логически безголовый — объявите техническую переменную (`dummy : BOOL;`).

## 2.7. `localId` ДОЛЖЕН БЫТЬ УНИКАЛЕН В ПРЕДЕЛАХ ВСЕГО POU

Не «в пределах сети», а в пределах POU. Совпадение `localId` между сетями
ломает схему. Мы нумеровали сквозным счётчиком на уровне POU:

```python
def _nid(self):
    self._next += 1
    return self._next
```

## 2.8. ВЫВОДЫ ВЫЗОВА FB СОПОСТАВЛЯЮТСЯ ПОЗИЦИОННО (грабли №3, стоила больше всех)

**Симптом:** `C32: Невозможно конвертировать тип 'BYTE' в тип 'BOOL'`, причём
схема типологически безупречна.

**Причина:** вызов FB объявлял **все шесть** выводов `[R, CY, AC, S, Z, P]`,
а читал **только три**: `S`, `Z`, `P`. Импортёр PLCopenXML сопоставляет
выводы **позиционно**, поэтому прочитанные легли на ПЕРВЫЕ три:

```
daa_s (BOOL) <- Rx (BYTE)   <-- вот эта ошибка
daa_z (BOOL) <- CY (BOOL)   <-- молча, но НЕВЕРНО
daa_p (BOOL) <- AC (BOOL)   <-- молча, но НЕВЕРНО
```

**Решение (общее, в генераторе):** вызов объявляет **только те выводы, которые
читает, и в порядке чтения**.

```python
def _prune_outputs(self):
    # собираем порядок чтения выводов для каждого блока
    used = {}
    for it in items:
        srcs = ...  # источники этой сети
        for s in srcs:
            if s.pin:
                used.setdefault(s.eid, []).append(s.pin)
    # переписываем список выводов блока = порядок чтения
    for net in self.networks:
        for k, it in enumerate(net._items):
            if it[0] != u"block": continue
            got = used.get(it[1])
            if got and got != list(it[4]):
                net._items[k] = (it[0], it[1], it[2], it[3], got, it[5], it[6])
```

Вызывать **до** развёртывания fan-out. И проверять отдельным скриптом: порядок
чтения должен быть **префиксом** списка объявленных выводов.

**Почему это не находилось:** все прочие вызовы FB читали ВСЕ свои выводы и в
порядке объявления — там позиционное совпадает с именованным. Достаточно было
ОДНОГО вызова с подмножеством выводов.

## 2.9. КАЖДЫЙ POU ДОЛЖЕН БЫТЬ СОБРАН ЗА ОДИН ИМПОРТ

Импорт POU по одному файлу (`app.import_xml(one)`) работает надёжнее, чем
один огромный XML: при ошибке видно, какой POU не встал. Но: **POU должен
импортироваться целиком** — дополнять существующий POU вторым XML нельзя.

Мы «патчили» схемы на уровне объектов `Pou` в памяти перед отрисовкой — это
надёжно, потому что на диск попадает уже готовый XML.

## 2.10. КООРДИНАТЫ: `x` И `y` ЛЕГКО ПЕРЕПУТАТЬ

У помощников вида `AND(n, a, b, x=None, y=None)` четвёртый аргумент — это
**координата x**, а не третий вход. Мы дважды передавали туда третий вход и
получали при отрисовке:

```
TypeError: %d format: a real number is required, not Src
```

**Правило:** вход, координата, вход, координата — считайте позиции. Для трёх
входов собирайте вложенный `AND(AND(a,b), c)`, а не `AND(a, b, c)`.

## 2.11. ИМЕНА, СОВПАДАЮЩИЕ С КЛЮЧЕВЫМИ СЛОВАМИ IEC

Разбор объявлений их принимает, **кодогенерация — нет**:

```
C9: Обнаружен недопустимый символ 'LD'
C9: Обнаружен недопустимый символ 'S'
C9: Обнаружен недопустимый символ 'R'
C189: ';' требуется вместо 'ARRAY'          (переменная DO в GVL)
C4: 'DO' не является компонентом 'GVL_IO'
```

Опасные имена: `LD`, `S`, `R`, `ST`, `SEL`, `BIT`, `EXP`, `TO`, `DO`, `STEP`,
`DATA`, `EQ`, `GE`, `GT`, `LE`, `LT`, `NE`.

**Решение:** переименовывать текстом уже готового XML (и в структурном
`<interface>`, и в текстовом дубле объявления, и во всех ссылках):

```python
RESERVED = { u"LD": u"LDx", u"S": u"Sx", u"R": u"Rx", u"ST": u"STx",
             u"SEL": u"SELx", u"DO": u"DOx", ... }
```

**Подвох:** если переименование делается в двух разных местах, определения и
потребители расходятся (`R` против `Rx`) — и получаете каскад `C0007/C0009`.
Держите **одну точку** переименования.

**Ещё подвох:** вход с именем `En` конфликтует с системным `EN` у FBD-блока
(`Недопустимое значение для свойства EN/ENO`). Переименуйте в `Enable`.

## 2.12. ПРОЧИЕ МЕЛОЧИ, КОТОРЫЕ ЛОВЯТСЯ ТОЛЬКО ОПЫТОМ

* `SHL(byte, 8)` даёт **0** — сдвиг на ширину типа. Сначала расширяйте до
  WORD: `SHL(BYTE_TO_WORD(x), 8)`.
* Маска `AND(x, INT#255)` над INT — `C32`. Используйте `MOD(x, 256)` или
  приводите тип.
* `NOT` принимает `ANY_BIT` (BYTE/WORD/DWORD), а не только BOOL — проверено
  экспериментом. Гипотеза «NOT только для BOOL» ложна.
* Логические `AND/OR/XOR` над BOOL и над BYTE — **одни и те же блоки**;
  смешивать BOOL и BYTE в одном блоке нельзя, но WORD+BYTE в арифметике
  компилируется нормально.
* Комментарий, закрытый раньше времени: последовательность `*)` внутри
  комментария обрывает его, остаток разбирается как код. У нас так сломались
  три модуля (`"порт CPM_*)"`).
