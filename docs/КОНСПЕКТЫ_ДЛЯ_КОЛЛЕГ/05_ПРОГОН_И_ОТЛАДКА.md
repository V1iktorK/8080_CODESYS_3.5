## 5.1. Первое: получите поскановый след

Без него отладка — гадание. Инструмент: скрипт, который открывает **уже
собранный** проект, логинится, запускает и опрашивает переменные.

```python
oa = scriptengine.online.create_online_application(app)
oa.login(scriptengine.OnlineChangeOption.Never, False)

while time.time() - t0 < SECONDS:
```

### ГЛАВНЫЙ ПРИЁМ: ЗАМЕДЛИТЬ ЗАДАЧУ

При `T#2ms` прогон даёт 2500 сканов за 5 секунд — скрипт не успевает опросить
ни одного интересного момента. **Пересоберите проект с интервалом `T#200ms`**:
прогон растягивается, и каждый опрос попадает на свой скан.

а `Trap_Phase` в этот момент — не 8, и такт не выполняется.

## 5.2. Замеры «что реально в памяти»

Отдельный скрипт читает память и состояние **в одной точке времени**:

```python
M = [u"GVL_MEM.Memory[%d]" % a for a in range(0x80, 0x80+20)]  # буфер 0080h
FCB = [u"GVL_MEM.Memory[%d]" % a for a in range(0x5C, 0x5C+16)]

STATE = [u"GVL_TEST.Mode", u"GVL_CPM.CCP_Cnt", ...]
```

Вопрос, который это решает: «диск загружен?», «строка команды попала в буфер?»,
«CCP реально исполнялся?».

**Пример из практики:** `Disk_Ready = TRUE, Dir_Used = 4` при `CCP_Phase = 0,
CCP_Cnt = 0` — то есть диск загружен, а консольный процессор даже не начинал.
Это сразу отсекло половину гипотез.

## 5.3. Пять причин, почему набор тестов «не идёт»

### 1. Тест не получает такта

Процессор разрешён условием `run = Enable AND NOT Halted`. Если `Enable`
приходит от другого блока, который выключен — такт не выполняется, PC стоит,
тест помечает FAIL.

**Диагностика:** `Step_Cnt` (счётчик тактов) не растёт — значит тактов нет.
Не ищите ошибку в командах: их не было.

### 2. Арбитраж двух программ

У нас в задаче четыре программы: `TEST_8080`, `PLC_PRG_CPM`, `TEST_CPM`,
`TEST_IO`. Они **делят один процессор**. Правила:

* порядок в задаче = порядок исполнения;
* если две программы пишут одну GVL-ячейку, побеждает **последняя**;
* тайминг скана сквозной: значения, записанные программой N, видны программе
  N+1 в **следующем** скане (если это GVL), либо в том же (если локальные).

**Наша ошибка:** `TEST_8080` шёл ПЕРВЫМ и каждые скан обнулял порт CP/M, когда
не владел процессором — и стирал значения, которые трап выставил в предыдущем
скане. Запись `PC := 0F100h` до процессора не доходила.

**Правило:** не владея ресурсом, **не трогайте** его. Пишите обратно текущее
значение, а не ноль:

```python
n.outvar(target, IF(n, own, new_value, I(n, target)))
```

### 3. Фаза живёт один скан

Переход `RUN -> STOP` был безусловным: фаза длилась ровно один скан. Но такт
выполняется только если скан совпал с «окном» другого автомата. Такт не
успевал.

**Решение:** считать **реальные** такты по изменению счётчика, а не сканы:

```python
step_chg = NE(Step_Cnt, step_prev)
tact := IF(f_run AND step_chg AND NOT stop_now, tact + 1, 0)
```

### 4. Набор закрывается раньше, чем выполнены проверки

Признак завершения «команда выполнена» срабатывает в начале выполнения, а
проверки фиксируются позже.

**Решение:** фиксировать проверки по факту завершения набора (`done`), а не по
номеру скана; и следить, чтобы все входные знаки были поданы
(`k >= len(SEQ)`) до закрытия.

### 5. Кольцевой буфер затирает то, что проверяют

Журнал консоли — кольцо на N байт. Проверка «первый символ = 'A'» перестаёт
работать, как только в буфере больше N знаков.

**Решение:** искать подстроку **в любом месте** буфера, а не по фиксированному
индексу:

```python
for i in range(0, 200):
    hits.append(AND(n, EQ(Log[i], 'A'), EQ(Log[i+1], '>')))
ok = ORL(n, hits)
```

## 5.4. Синхронизация с внешним устройством через флаг готовности

Мы подавали символы в консоль через `Char` + `Ready`. Ловушки:

* **Кто пишет последним, тот и прав.** Если тест и «устройство» пишут один
  флаг, порядок в задаче решает, чьё значение останется.
* **Односкановый строб теряется.** Устройство принимает данные не каждый скан;
  держите сигнал выставленным, пока не придёт подтверждение.
* **Нельзя ждать подтверждения от того, кто сам ждёт вас.** У нас `CCP` живёт
  ВНУТРИ трапа, поэтому признак `Trap_Active` истинен почти всегда — ждать
  `NOT Trap_Active` бессмысленно.

**Рабочая схема:** счётчик выдержки (`hold`) тикает, знак меняется каждые
`DWELL` сканов, а `DWELL` подбирается под скорость приёма (у нас 20 сканов).

## 5.5. Онлайн-сессия стартует с СОХРАНЁННЫХ значений

**Это отдельная ловушка, стоившая дня.**

`oa.start()` поднимает приложение со значениями, **сохранёнными в проекте**
от прошлого прогона — а не с инициализаторов объявлений. То есть
`Mode = 0`, `DoneCpm = TRUE` и прочее «наследство».

**Хуже:** локальные переменные POU **тоже сохраняются**. Автомат стартовал не
с фазы IDLE, а с той, на которой его застал прошлый запуск.

**Решение — явный сброс перед стартом:**

```python
RESET = ((u"GVL_TEST.Mode", u"1"), (u"GVL_TEST.Run", u"TRUE"),
         (u"GVL_TEST.Done8080", u"FALSE"), ...)
for nm, val in RESET:
    oa.set_prepared_value(nm, val)
    oa.write_prepared_values()          # ПО ОДНОМУ, иначе применится последнее
```

И **одноразовый сброс автоматов в FBD**:

```python
# если счётчик сканов = 0 (сразу после сброса) - фаза принудительно в IDLE
acc = SEL(n, EQ(Scans, 0), acc, I(n, PH_IDLE))
```

## 5.6. Чек-лист «тесты не проходят»

1. Поскановый след снят? Задача замедлена?
2. Растёт ли счётчик тактов? (если нет — тест не получает процессора)
3. Кто ещё пишет те же GVL-ячейки? Кто последний в задаче?
4. Не обнуляет ли одна программа то, что выставила другая?
5. Все входные данные поданы до закрытия набора?
6. Не читаете ли вы ячейку в той же сети, где её пишете?
7. Состояние сброшено перед стартом (включая локальные переменные)?
8. Прогнали дважды? Первый прогон может пройти на прогретом состоянии.
