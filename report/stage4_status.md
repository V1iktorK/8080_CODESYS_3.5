## 3. ЧТО НЕ ПОЛУЧИЛОСЬ И ПОЧЕМУ (точно)

### 3.1. Главное открытие этапа: до сих пор проект НИ РАЗУ не проходил кодогенерацию

Пока в проекте нет конфигурации задач, CODESYS **только разбирает объявления** и
пишет «Компиляция завершена -- 0 ошибок». Кодогенерация включается вместе с
первой задачей. Поэтому все четыре этапа схема «компилировалась» с нулём
ошибок, ни разу не проверив то, что видит только генератор кода.

Проба `gen_probe4d.py` (только старый слой, без единой строки этапа 4, но С
задачей) дала **315 ошибок**. То есть «0 ошибок» в журналах этапов 3.2–3.6 были
не подтверждением работоспособности, а следствием отсутствия задачи.

### 3.3. ОСТАВШАЯСЯ ОШИБКА (одна, она и блокирует прогон)

```
Компиляция: Error: C23: Для 'AND' необходимо как минимум '2' операндов
Компиляция завершена -- 1 ошибок, 0 предупреждений : загрузка невозможна
```

Локализация (строгий разбор выгрузки `stage4_full_reexport.xml` через
`tools/find_and4.py` и `tools/show_bad_and.py`):

* блоков `AND/OR/XOR` во всём проекте — **1266**, из них **ровно 1** повреждён;
* повреждён блок **`FB_IO_Dispatch`**, `typeName="AND"`, входов **1** вместо 2;
* пропал элемент `inVariable`, стоявший непосредственно перед блоком
  (в выгрузке: `… inVariable miss → inVariable rd_ok → block AND → inVariable cons_in → block AND(1 вход) …`).

То есть это **не ошибка схемы и не ошибка задания**: генератор записал блок с
двумя входами (проверено `tools/find_and2.py` по сгенерированному XML), а
импортёр CODESYS молча потерял вход вместе с элементом — ровно тот класс
дефектов, который в журнале описан в п. 4.3 и 11.2 («связь теряется МОЛЧА», а
контроль качества видит только число блоков и пустые входы, поэтому потерю не
замечает).

Что уже испробовано для обхода (без результата):

1. защёлка `GVL_CPM.ConIn_Ready` в переменную POU (устранение двойного чтения) —
   ошибка на том же месте;
2. замена блока `AND` на `SEL` (в проекте стало на один `AND` меньше — 1266
   вместо 1267), повреждённый блок остался тем же.

**Что нужно, чтобы закрыть этап:** найти в `FB_IO_Dispatch` конкретную сеть,
породившую повреждённый `AND` (сопоставив `localId` выгрузки с элементом
генератора), и переписать её так же, как это принято в проекте: провести сигнал
через переменную POU. Метод поиска и точная процедура описаны в п. 4 ниже.

## 4. ЧТО ИМЕННО НУЖНО СДЕЛАТЬ, ЧТОБЫ ПОЛУЧИТЬ ТАБЛИЦУ PASS/FAIL

Шаг 1. Найти сеть-источник (5 минут, без CODESYS):
```
python tools\find_and4.py                 # покажет POU и localId повреждённого блока
python tools\show_bad_and.py              # покажет соседние элементы выгрузки
```
Шаг 2. Сопоставить соседние элементы с исходной схемой:
`grep -n "cons_in" generator\pou_io.py` — повреждённый `AND` стоит сразу после
`inVariable cons_in`; в `FB_IO_Dispatch` это сеть консольного канала (СЕТЬ 4).
Шаг 3. Переписать соответствующий `outvar` так, чтобы вход блока брался из
переменной POU, а не из только что созданного `inVariable` (образец — уже
сделанное `cin_rdy`), затем:
```
generator\tools\run_stage4.ps1 -Script generator\gen_stage4.py -MaxAttempts 10 `
    -RunTimeoutSec 1800 -QuietSec 5 -NoSrcCopy
```
Признак успеха — `Компиляция завершена -- 0 ошибок` на ВТОРОЙ сборке (после
`[OK] сборка с конфигурацией задач выполнена`), затем в логе `[OK] login(...)` и
строки `t=... с: Scans=... | Mode=... | Pass_Cnt=...`.

Шаг 4. Отчёт формируется автоматически: `report/stage4_report.md`
(`run_online.write_report`), таблица «тест → ожидание → факт → PASS/FAIL»
по всем 199 кейсам, плюс расшифровка журнала консоли CP/M.

## 5. ЧТО ФИЗИЧЕСКИ НЕЛЬЗЯ ПРОВЕРИТЬ БЕЗ РЕАЛЬНОГО ПЛК

1. **Адаптер C** (`FB_IO_Adapter_HW`, адреса `%IB0/%QB0/%IW0/%QW0`): модулей
   ввода-вывода нет, адреса ни с чем не связаны. Проверено только, что
   компилируется. Реальный обмен — только на профиле C.
2. **Реальные каналы DI/DO/AI/AO**: в симуляции это массивы `GVL_IO`, то есть
   проверяется логика слоя, а не электрика (уровни, помехи, время
   установления).
3. **Watchdog по времени скана**: `FB_Watchdog` считает СКАНЫ, а не
   миллисекунды (библиотека измерения времени не используется сознательно).
   Соответствие `Limit_Scans` реальному времени скана на целевом ПЛК надо
   измерять на месте.
4. **Производительность**: замеры 80–130 сканов/с получены на симуляции ПК.
   Реальный 8080 быстрее эмулятора в 20–100 раз (оценка плана) — на целевом
   ПЛК `Tacts_Per_Scan` придётся подбирать.
